## User Scenarios & Testing *(mandatory)*

### User Story 1 - Caller gets an IMDb-grounded rating answer in a chat turn (Priority: P1)

A client with an existing `chatId` asks a rating question - "what's the IMDb rating of Inception?", "which of {A, B, C} is the highest rated?", or "which of {A, B, C} are above 7?". The chat routes from slice 003 run the single agent, which now has the ChatPlanner rating tools attached. The agent calls `GetMovieRating`, `CompareMovieRatings`, or `FilterMoviesByRating` as appropriate and composes its answer from the returned IMDb primary rating plus the Rotten Tomatoes / Metacritic / Awards / Box Office context those tools return.

**Why this priority**: Ratings are the single most asked-about attribute in this product's chat today, and the Function App's rating answers never land without these three tools. Without this story, slice 004 does not change the chat's answer quality on its primary question class. P1 because the whole point of this slice is to restore the Function App's answer surface on top of the slice 003 agent, and ratings are the biggest observable gap.

**Independent Test**: Manual, like slice 003. Create a `chatId` via `GET /api/chat/start`, then `POST /api/chat/{chatId}/ask` with "what's the IMDb rating of Inception?" and verify (a) the response is 200, (b) the assistant `text` names the IMDb rating value OMDb returned at test time (e.g. "8.8") and specifically identifies it as the IMDb rating rather than citing a TMDb vote average, (c) the identical request against the Function App's `Chat-Ask` endpoint names a comparable IMDb rating value. Repeat with "which is highest rated: Inception, The Dark Knight, Interstellar?" to exercise `CompareMovieRatings`, and "which of {A, B, C, D} are at or above 7?" to exercise `FilterMoviesByRating`. Run the three checks locally and against the deployed revision.

**Acceptance Scenarios**:

1. **Given** a session created by slice 002, **When** the caller sends `POST /api/chat/{chatId}/ask` with `{ "Input": "what's the IMDb rating of Inception?" }`, **Then** the response is 200 and the assistant message's `text` contains the IMDb rating OMDb returned at test time (for example "8.8"), presented as the IMDb rating. The assistant MUST NOT answer the rating question from a TMDb `vote_average` carried in earlier search context (verified by naming a value that matches OMDb's current rating for Inception rather than TMDb's).
2. **Given** the same session, **When** the caller sends `POST /api/chat/{chatId}/ask` with `{ "Input": "which has the highest IMDb rating: Inception, The Dark Knight, Interstellar?" }`, **Then** the assistant's answer names the film OMDb reports as highest-rated at test time, with its IMDb rating value, and does so from an IMDb comparison rather than a TMDb vote average.
3. **Given** the same session, **When** the caller sends `POST /api/chat/{chatId}/ask` with `{ "Input": "which of The Godfather, Jaws, Howard the Duck, and Rocky are rated 7 or above?" }`, **Then** the assistant lists exactly the films whose OMDb IMDb rating is at or above 7.0 at test time (`FilterMoviesByRating` uses `>=`, matching the Function App's `actualRating >= minimumRating`).
4. **Given** OMDb returns an error or a `Response: "False"` for one of the ids in a comparison or filter call, **When** the turn runs, **Then** the comparison/filter still succeeds for the remaining ids: `AllMovies` in `CompareMovieRatings` contains only the lookups where `IsSuccess == true` (the failed id is dropped), and the winner is selected from the subset of those successful lookups whose `ImdbRating` parses as a number - a successful lookup with `ImdbRating == "N/A"` remains in `AllMovies` but is excluded from winner selection, matching `OpenMovieDbAgent.CompareMovieRatings`. An OMDb failure on a single id MUST NOT cause the chat turn to return non-200.

### User Story 2 - Caller asks for a trailer and gets back a playable embed (Priority: P1)

A client asks "show me the trailer for Dune" (or, after naming a film earlier in the conversation, "show me the trailer for that one"). The agent calls `HandleTrailerRequest` with the title the user named - resolving pronouns itself, since the tool does not see the conversation - and TrailerAgent returns the pre-wrapped `[TRAILER]{youtube-url}[/TRAILER]` embed string. The assistant includes that exact wrapper in its `SystemMessage` so the frontend renders the player inline.

**Why this priority**: Trailers are the second-biggest observable gap between slice 003's chat and the Function App's chat. The Function App's `[TRAILER]` wrapper is a hard contract with the frontend player; without the tool there is no reliable way for the agent to produce a working one. P1 because trailers and ratings are the two tool surfaces this slice exists to port.

**Independent Test**: Manual. Create a `chatId`, then `POST /api/chat/{chatId}/ask` with `{ "Input": "show me the trailer for Dune" }`. Verify the response is 200 and the assistant `text` contains exactly one `[TRAILER]https://www.youtube.com/watch?v={key}[/TRAILER]` block whose key refers to a YouTube video that plays Dune's trailer. Follow up on the same session with `{ "Input": "show me the trailer for it" }` and verify the agent still returns a `[TRAILER]` block for Dune (pronoun resolved by the model, not the tool). Run locally and against the deployed revision.

**Acceptance Scenarios**:

1. **Given** a session, **When** the caller sends `POST /api/chat/{chatId}/ask` with a trailer request naming a film, **Then** the response is 200 and the assistant `text` contains exactly one `[TRAILER]https://www.youtube.com/watch?v={key}[/TRAILER]` substring whose `{key}` is the TMDb-returned YouTube video key.
2. **Given** a prior assistant turn named a specific film and the next user message says "show me the trailer for it", **When** the turn runs, **Then** the agent calls `HandleTrailerRequest` with the film's title (not the literal string "it") and the response's assistant `text` contains a `[TRAILER]` block for that film.
3. **Given** the user asks for a trailer for a title TMDb has but has no `Type == "Trailer" / Site == "YouTube"` video for, **When** the tool runs, **Then** the tool returns the Function App's "No YouTube trailer is available for '{title}'" error payload and the assistant tells the user plainly rather than substituting a different film's trailer. The response is 200.
4. **Given** `HandleTrailerRequest` is called with an empty or `"UNKNOWN"` title (the model failed to resolve a referent), **When** the tool runs, **Then** the tool returns the Function App's "No movie title was supplied" error+hint payload and the assistant does not emit a `[TRAILER]` block. The response is 200.

### User Story 3 - Response envelope includes a Wikipedia-grounded funny fact when one is available (Priority: P2)

Every chat turn (both `/ask` and `/ask/v2`) runs `SafeGenerateFunnyFactAsync` alongside the model call. When the user's input names a specific entity Wikipedia and Wikidata can ground (confidence > 0.5) and the grounded completion produces a non-`NONE` fact, the session's `FunnyFact` is updated and the response envelope's `funnyFact` field carries that fact. Otherwise the session's `FunnyFact` is left as-is (`null` on a fresh session; the previous turn's fact on a returning one), matching the Function App's "null MUST NOT overwrite" behaviour (FR-007).

**Why this priority**: The funny fact is a decorative but client-visible field. Slice 003 ships `funnyFact: null` on every response; this slice makes it a real string when Wikipedia agrees. P2 because the chat still answers without it - a Wikipedia outage or a non-groundable query already quietly leaves the session's existing value in place and must continue to.

**Independent Test**: Manual, on a FRESH `chatId` so there is no previous fact to inherit. `POST /api/chat/{chatId}/ask` with `{ "Input": "tell me about Inception" }`. Verify (a) 200, (b) in the usual case, the response's top-level `funnyFact` is a non-null, non-empty string under ~100 characters. If the first attempt lands in the `NONE`/below-gate branch (model non-determinism, per US3 scenario 1's rerun allowance), re-run on a new fresh `chatId` with the same or a different qualifying input until the ported path produces a non-null fact. Then, on a SECOND fresh `chatId` separate from the one above, call `POST /api/chat/{chatId}/ask` with `{ "Input": "popular movies last year" }` and verify `funnyFact` is `null`. Both routes carry the field. Run locally and against the deployed revision.

**Acceptance Scenarios**:

1. **Given** a FRESH session (no prior turns), **When** `POST /api/chat/{chatId}/ask` is called with an input for which the Function App's `Chat-Ask` endpoint returns a non-null `funnyFact` at test time (confirmed by a reference call made moments before; the Function App is the behavioural ground truth under Principle III), **Then** the response is 200. In the usual case the response's top-level `funnyFact` is a non-null, non-empty string whose content is grounded in the entity's Wikipedia summary. The grounded completion returning `NONE` is a legal outcome - the port's model call is independent of the Function App's, so the two can land in different branches for the same input - and in that case `funnyFact` MUST be `null`. If the first attempt lands in the `NONE`/below-gate branch, the test is re-run on a new fresh `chatId` with the same or a different qualifying input until the ported path produces a non-null fact in at least one run, at which point the grounded-in-summary assertion applies.
2. **Given** a FRESH session, **When** `POST /api/chat/{chatId}/ask/v2` is called with the same qualifying input as scenario 1, **Then** the response is 200 and the funny-fact outcome follows the same two-branch rule as scenario 1, with the same rerun allowance. (The field is the same on both routes.)
3. **Given** a FRESH session, **When** either route is called with an input that names no specific entity (generic query like "popular movies last year"), **Then** `funnyFact` is `null`.
4. **Given** a FRESH session with Wikipedia or Wikidata unreachable, **When** either route is called, **Then** the response is 200, `funnyFact` is `null`, and the model-produced assistant answer is still returned. The server MAY log a warning (when an exception reaches `SafeGenerateFunnyFactAsync`'s catch) or an error (when `GetEnhancedInfo`'s inner catch handles it); a non-2xx response from Wikipedia or Wikidata that does not throw returns `null` silently. No log line and no response body contains secret material.
5. **Given** a FRESH session where the Wikipedia + Wikidata lookup for the detected entity produces a confidence score at or below 0.5, OR the grounded completion returns `NONE` (even above the gate), **When** the turn runs, **Then** `funnyFact` is `null` rather than an ungrounded fallback.
6. **Given** a RETURNING session whose previous turn successfully set `FunnyFact` to a non-empty string, **When** the next turn's input names no entity (or Wikipedia is unreachable, or confidence fails, or the grounded completion returns `NONE`), **Then** the response's `funnyFact` is the previous turn's string, not `null` - the session's existing value is preserved (FR-007 clause 4).

### User Story 4 - Agent can enrich an answer with Wikipedia context tools (Priority: P3)

The agent has two context tools: `GetChatContext(entityName, entityType)` and `GetMovieContext(userQuery)`. The agent may call them while composing an answer to produce a 1-2 sentence Wikipedia-grounded addition. `GetChatContext` returns a JSON object with `Entity`, `Summary`, `Facts`, `Confidence` whenever `GetEnhancedInfo` returns a non-null `WikipediaResult` - including a result whose `Summary` is null, `Facts` is null, and `Confidence` is 0.0 (the "both lookups returned non-2xx without throwing" case); there is no confidence gate. `GetChatContext` returns `null` only when `GetEnhancedInfo`'s outer try/catch handled a thrown exception and returned null. `GetMovieContext` returns a short grounded blurb produced via a second IChatClient completion, gated at `confidence > 0.5` and filtered through `NullIfNone`; it returns `null` for below-gate confidence, `NONE` replies, or null `GetEnhancedInfo` results.

**Why this priority**: Context tools are the richness ceiling on the agent's answers. They are not what the user explicitly asks for, so a missing call does not look like a defect - which is why they are P3 - but their absence is why slice 003's chat reads flat compared to the Function App's. The port is in scope because the Function App offers them.

**Independent Test**: Manual. Create a `chatId`, then `POST /api/chat/{chatId}/ask` with `{ "Input": "tell me about Christopher Nolan" }`. Verify (a) 200, (b) the assistant answer is a well-formed response (presence of a Wikipedia-grounded clause is best-effort and model-dependent; the Function App itself has no server-visible proof that the tool fired beyond default framework tracing, which may or may not be enabled in slice 003). Call the same input against the Function App's `Chat-Ask` and verify a Wikipedia-grounded clause in the answer looks comparable in richness. Run locally and against the deployed revision.

**Acceptance Scenarios**:

1. **Given** a session, **When** the user asks about a well-known entity (`"tell me about Christopher Nolan"`), **Then** the response is 200 and the assistant answer may include a 1-2 sentence Wikipedia-grounded context clause. (The clause is best-effort; its presence is not required by this scenario, only that no error occurred and the response is 200.)
2. **Given** the detected entity is at or below the confidence gate (`<= 0.5`), **When** `GetMovieContext` is invoked, **Then** `GetMovieContext` returns `null` and the assistant's answer is composed without that blurb. (`GetChatContext` is NOT gated by confidence - it returns its JSON object whenever `GetEnhancedInfo` returned any result, including a zero-confidence one; see Key Entities.) The turn still returns 200.
3. **Given** `GetChatContext` is invoked and `GetEnhancedInfo`'s outer catch handled a thrown exception (so `GetEnhancedInfo` returned null), **When** the tool runs, **Then** it returns `null` and the assistant proceeds. **Given** instead that both `SearchWikipedia` and `QueryWikidata` returned null without throwing (non-2xx responses), `GetEnhancedInfo` returns a `WikipediaResult` with `WikipediaContent = null`, `StructuredData = null`, `ConfidenceScore = 0.0`, and `GetChatContext` therefore returns a JSON object with `Entity`, `Summary = null`, `Facts = null`, `Confidence = 0` - not `null`. This matches the Function App's single `if (wikipediaInfo == null) return null` guard. In every path, no tool failure escalates to a 503.

### Edge Cases

- **Model emits an invalid IMDb id for a rating tool**: `GetMovieRating` returns `{ "Error": "Movie not found for IMDb ID: {id}" }`. The agent reads the error and either retries with a corrected id or tells the user plainly. The turn still returns 200.
- **OMDb returns `ImdbRating: "N/A"`** for an id (e.g. a very obscure or recent release): `CompareMovieRatings` and `FilterMoviesByRating` skip that id (its rating fails `double.TryParse`) and continue; the Function App's exact behaviour.
- **Model passes a mis-formatted comma list** to `CompareMovieRatings` or `FilterMoviesByRating` (stray spaces, trailing commas): each id is trimmed and empty entries flow through OMDb lookups as misses, matching the Function App's `.Split(',').Select(id => id.Trim())`.
- **The user asks for a trailer with no title**: `HandleTrailerRequest` receives `""` or `"UNKNOWN"` and returns the error+hint payload. The agent includes no `[TRAILER]` block.
- **The user asks for a trailer for a title TMDb cannot find**: `HandleTrailerRequest` returns the "No movie found matching '{title}'" payload. The agent surfaces that plainly and includes no `[TRAILER]` block.
- **Wikipedia 404s on a known entity whose article name does not match the user's spelling**: `SearchWikipedia` returns null (the 404 is not an exception, just `!IsSuccessStatusCode`), `CalculateConfidence` scores it 0.0 or 0.4 (0.4 if Wikidata still bound structured facts, 0.0 otherwise), and the funny-fact pipeline returns `null` (below the 0.5 gate). `GetMovieContext` likewise returns `null`. `GetChatContext` does NOT return null here - it returns a JSON object with `Summary = null`, `Facts` = whatever Wikidata bound (possibly null), `Confidence = 0.0` or `0.4`, matching the Function App's `if (wikipediaInfo == null) return null` guard which only fires when `GetEnhancedInfo`'s catch handled a throw. The turn still runs normally.
- **Wikidata SPARQL times out** (`query.wikidata.org` is slow): the typed HttpClient's 15-second timeout fires inside `QueryWikidata`, the thrown `TaskCanceledException` propagates out of `QueryWikidata` into `GetEnhancedInfo`'s outer try/catch, and `GetEnhancedInfo` returns `null`. The Wikipedia summary already fetched is discarded in that path - matching the Function App's `try { Wikipedia; Wikidata; return WikipediaResult } catch { logger.LogError; return null }` shape. The funny fact and context tools therefore return `null`.
- **Wikidata SPARQL returns a non-2xx response** (not a timeout, not a throw): `QueryWikidata` returns `null` without throwing. `GetEnhancedInfo` then returns a `WikipediaResult` with `WikipediaContent` populated and `StructuredData = null`, so if the Wikipedia summary length exceeds 100 characters the confidence score is 0.6 and clears the gate. In this path a funny fact can still land from the Wikipedia summary alone.
- **DetectEntity returns a dirty string** (quotes, trailing period, lowercase `none`): `ParseDetectedEntity` strips quotes/periods/whitespace and compares case-insensitively, matching the Function App; a dirty "NONE" is correctly treated as no entity, not sent to Wikipedia.
- **The user names an actress and the model's DetectEntity returns `TYPE=actress`**: `ParseDetectedEntity` normalises `actress`, `person`, `cast` to `actor`, so the actor SPARQL query is run, not the movie default.
- **Model repeats a rating tool call on the same id twice in a turn**: not deduped by this slice; two concurrent OMDb lookups run, same as the Function App. This is observable behaviour, not a defect.
- **The OMDb key env var is missing in the running container**: `OpenMovieDbAgent`'s constructor throws `ArgumentNullException` at DI resolution, which fails the chat route per slice 003's generic 503 contract. Startup itself is not required to validate the OMDb key; the Function App validates lazily.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: The slice MUST port `Prompts/ChatPlanner.cs` into the API as a scoped service whose `CreateTools()` returns exactly these six `AIFunctionFactory.Create` entries, in this order and with the Function App's exact `[Description]` text and parameter signatures: `HandleTrailerRequest(string movieTitle)`, `GetMovieRating(string imdbId)`, `CompareMovieRatings(string imdbIds)`, `FilterMoviesByRating(string imdbIds, double minimumRating)`, `GetChatContext(string entityName, string entityType = "movie")`, `GetMovieContext(string userQuery)`. No tool is added, renamed, or dropped. In particular, `GenerateEnhancedFunnyFact`, `DetectEntity`, `ParseDetectedEntity`, and `NullIfNone` are ported but MUST NOT be registered as tools, matching the Function App.
- **FR-002**: `Program.cs` MUST fold the six ChatPlanner tools into the existing single `AIAgent` from slice 003 by appending `chatPlanner.CreateTools()` to the agent's existing tool list (`.. theMovieDbFunctions.CreateTools(), .. DateTimeKernelFunctions.CreateTools(), .. chatPlanner.CreateTools()`). No second agent is introduced; no per-tool DI pattern that bypasses the single agent is introduced.
- **FR-003**: `Agents/OpenMovieDbAgent.cs` MUST be ported as-is (behaviour-preserving). Its constructor reads the OMDb API key from `IConfiguration` under the key path `OpenMovieDb:Api-Key`, matching the Function App's lookup. `OpenMovieDbAgent` MUST be registered scoped. `CompareMovieRatings(List<string>)` and `FilterMoviesByRating(List<string>, double)` MUST fan out OMDb lookups concurrently via `Task.WhenAll`, preserving positional order (the Function App's `GetManyAsync` pattern). `ImdbRating` MUST be the primary rating returned; `RottenTomatoesRating` and `MetacriticRating` are secondary context. In `CompareMovieRatings`, failed lookups (`IsSuccess == false`) MUST be excluded from `AllMovies`, but successful lookups whose `ImdbRating` is non-numeric (e.g. `"N/A"`) MUST remain in `AllMovies` and MUST be excluded only from winner selection (which uses `double.TryParse` with `NumberStyles.Any` and `CultureInfo.InvariantCulture`). In `FilterMoviesByRating`, non-numeric ratings fail the predicate and are not in the returned list. `CompareMovieRatings` MUST return two distinguishable error messages matching the Function App exactly: `"No valid movies found for comparison"` when zero successful lookups came back (the `!movieRatings.Any()` branch), and `"No movies with valid IMDb ratings found"` when there are successful rows but none have a numerically parseable `ImdbRating` (the `highest == null` branch, which still returns `AllMovies` populated with the non-numeric successful rows). Both set `IsSuccess: false`.
- **FR-004**: `Agents/TrailerAgent.cs` MUST be ported as-is. It MUST take `TMDbClient` through its constructor (the one `TMDbClient` singleton slice 003 registers) and MUST be registered scoped. Its `GetTrailerForTitle(string movieTitle)` MUST (a) return the Function App's "No movie title was supplied" error+hint payload when the title is null/whitespace or equals `"UNKNOWN"` (case-insensitive), (b) call `tmdbClient.SearchMovieAsync(title)` and take the first result, returning the "No movie found matching '{title}'" error payload when there is none, (c) call `tmdbClient.GetMovieVideosAsync(match.Id)` and select the first video with `Type == "Trailer"` and `Site == "YouTube"`, ordered by `Official` descending then `Size` descending (the same ordering slice 003's hydration path uses - FR-010 of slice 003 - so the two paths never pick different trailers for the same film), (d) return the Function App's success payload including `EmbedInSystemMessage = $"[TRAILER]https://www.youtube.com/watch?v={trailer.Key}[/TRAILER]"` exactly, and (e) return the Function App's "No YouTube trailer is available for '{title}'" error payload when no video matches. `TrailerAgent` MUST NOT take an `IChatClient` (the Function App removed the title-extraction completion and the keyword gate; both are gone here too).
- **FR-005**: `Agents/WikipediaSearchAgent.cs` MUST be ported as-is. It MUST be registered via `services.AddHttpClient<WikipediaSearchAgent>(httpClient => ...)` with (a) a `User-Agent` header built from two `ProductInfoHeaderValue` entries - the first is `"{serviceName}/{serviceVersion}"` using this API's assembly name and informational version, the second is `"(+https://github.com/<owner>/<movie-tracker-api repo>)"` as the Wikimedia-policy comment - and (b) `Timeout = TimeSpan.FromSeconds(15)`. The agent MUST NOT be registered a second time via `AddScoped<WikipediaSearchAgent>()`; the typed-client registration is the one that resolves. The ported `SearchWikipedia` MUST hit `https://en.wikipedia.org/api/rest_v1/page/summary/{Uri.EscapeDataString(entityName)}` with no extra GETs; `QueryWikidata` MUST `POST` form-encoded `query` + `format=json` to `https://query.wikidata.org/sparql` with the entity-type-dispatched SPARQL (movie / actor / director; everything else falls back to movie). The JSON deserialisation MUST keep the Function App's `[JsonPropertyName]` attributes verbatim on `WikipediaSummary` (lowercase `title`, `extract`, `thumbnail`); `PropertyNameCaseInsensitive = true` MUST NOT be substituted. `CalculateConfidence` MUST score `+0.6` for `wikipedia.Summary.Length > 100` and `+0.4` for any Wikidata structured facts, capped at 1.0 - the Function App's exact weights.
- **FR-006**: ChatPlanner MUST be registered scoped and MUST receive the same bare `IChatClient` the agent is built on. ChatPlanner's single-shot completions (`DetectEntity`, the final completions in `GenerateEnhancedFunnyFact` and `GetMovieContext`) MUST run against the bare `IChatClient` without the agent's tool set and without the structured-output JSON response format from slice 003's `MovieListResponse` schema. The `IChatClient` registration is the one slice 003 already provides; this slice does not add a second registration.
- **FR-007**: The agent-turn pipeline MUST run `SafeGenerateFunnyFactAsync(input)` alongside the model call, matching `Functions/Function.cs`:
  1. The task is kicked off BEFORE the user message is appended and BEFORE the compaction/model call runs (`Task<string?> funnyFactTask = SafeGenerateFunnyFactAsync(input);`), so Wikipedia latency does not block the critical path.
  2. The task is awaited AFTER the model's reply is appended to the stored history.
  3. The task body is a try/catch over `chatPlanner.GenerateEnhancedFunnyFact(input)` that returns `null` on any exception and emits an `ILogger` warning naming the exception. A thrown funny-fact task MUST NOT fail the turn.
  4. If the awaited result is non-null, the session's `FunnyFact` is set to it. If the awaited result is null - whether because the input named no entity, the confidence score failed the gate, `NullIfNone` filtered a `NONE` reply even above the gate, Wikipedia / Wikidata returned non-2xx, or an exception reached a catch - the session's `FunnyFact` is NOT overwritten (the Function App preserves a previous turn's fact rather than clearing it on a quiet turn).
- **FR-008**: `GenerateEnhancedFunnyFact` MUST be ported as-is: detect the entity via the bare `IChatClient`, call `WikipediaSearchAgent.GetEnhancedInfo(name, type)` with the detected type (movie / actor / director, never silently defaulting to "movie" for a person), gate at `wikipediaInfo?.ConfidenceScore is not > 0.5`, and run a second grounded completion whose prompt interpolates ONLY `WikipediaContent.Summary`. The grounded prompt MUST instruct the model to answer `NONE` rather than inventing, and `NullIfNone` MUST turn that answer back into `null` so an ungrounded fact never reaches the client.
- **FR-009**: `GetMovieContext` MUST be ported as-is: detect the entity, gate at `confidence > 0.5`, run a second grounded completion whose prompt interpolates both `WikipediaContent.Summary` and `WikidataInfo.StructuredFacts`, and apply `NullIfNone` to the result. `GetChatContext` MUST be ported as-is: look up `WikipediaSearchAgent.GetEnhancedInfo(entityName, entityType)` (the Function App defaults `entityType` to `"movie"`) and return a JSON object with `Entity`, `Summary`, `Facts`, `Confidence` whenever `GetEnhancedInfo` returns a non-null `WikipediaResult` (regardless of the confidence score, matching the Function App's single `if (wikipediaInfo == null) return null` guard), or `null` when `GetEnhancedInfo` returned null. `GetChatContext` MUST NOT be gated by confidence; `GetMovieContext` MUST be. Neither tool MUST be gated by any additional check beyond those the Function App performs.
- **FR-010**: `ParseDetectedEntity` MUST normalise the model's detected type: `actor`, `actress`, `person`, `cast` all map to `"actor"`; `director`, `filmmaker` map to `"director"`; everything else falls back to `"movie"`. The parser MUST strip surrounding quotes, periods and whitespace, and MUST treat `"NONE"` (any case) as no entity, as the Function App does. Breaking this normalisation sends every actor / director query onto the movie SPARQL query, which matches nothing - a port defect, not an acceptable simplification.
- **FR-011**: The response envelope for both `/api/chat/{chatId}/ask` and `/api/chat/{chatId}/ask/v2` MUST serialize the session's current `FunnyFact` into the top-level `funnyFact` field. This replaces slice 003's always-null behaviour (slice 003's FR-004). The field type and nullability (nullable string) stay as slice 003 defined them; the wire JSON shape otherwise does not change. If the funny-fact task threw and was caught, `funnyFact` reflects whatever value the session already held (null for a fresh session, the previous turn's string for a returning one).
- **FR-012**: The OMDb API key MUST be a Key Vault secret surfaced into the running container as an environment variable, matching the pattern slice 003 already uses for `azure-openai-key` and `themoviedb-api-key`. In this repo that pattern is: `infrastructure/key-vault.bicep` declares the vault only (not the per-secret resources), and the owner creates the secret in that vault once, out of band, before deploy. Specifically for this slice: (a) `infrastructure/container-app.bicep` MUST add an entry to its `secrets` array with `name: 'omdb-api-key'` and `keyVaultUrl: '${keyVaultUri}/omdb-api-key'` under the Container App's user-assigned managed identity, alongside the existing `azure-openai-key` and `themoviedb-api-key` entries; (b) `infrastructure/container-app.bicep` MUST inject an environment variable `name: 'OpenMovieDb__Api-Key'` with `secretRef: 'omdb-api-key'`. The `.NET` configuration path `OpenMovieDb:Api-Key` resolves against this env var at runtime. **OWNER step**: before the first deploy that includes this slice, the owner MUST set a Key Vault secret named `omdb-api-key` in the vault referenced by `keyVaultName`, with the new OMDb key as its value. This matches how `azure-openai-key` and `themoviedb-api-key` were seeded; `infrastructure/key-vault.bicep` is NOT changed to declare the secret. **Recorded Development-Workflow exception**: this is a documented manual pre-deployment step, which the constitution's Development Workflow forbids ("A documented manual pre-deployment step is a design defect to be removed, not an instruction to be followed"). The exception is taken for parity with the slice 003 pattern already in `infrastructure/container-app.bicep`; removing the manual step for all three secrets at once is deferred to a dedicated follow-up slice. This spec does not introduce the problem - it inherits it - but names it rather than launder it as compliance.
- **FR-013**: No OMDb key value MUST appear in `appsettings.json`, `appsettings.Development.json`, or any other repository file (constitution Principle V). Local development MUST source the OMDb key from `dotnet user-secrets` under the same `OpenMovieDb:Api-Key` key path. The quickstart MUST document the `dotnet user-secrets set "OpenMovieDb:Api-Key" "<key>"` command.
- **FR-014**: The OMDb key provisioned for this slice MUST be a newly issued key from omdbapi.com, not the key present in the `movie-tracker-backend` repository's committed `appsettings.json`. The Function App's committed key MUST be treated as compromised per Principle V (it is in git history) and MUST NOT be reused. The repository MUST NOT record which key value was chosen; only the fact that it is new.
- **FR-015**: `OpenMovieDbAgent` MUST be the only component that depends on `IOmdbClient` / `AsyncOmdbClient`. The NuGet reference (`OMDbApiNet` or equivalent) MUST be added to `MovieTracker.Api.csproj`. The slice MUST NOT add any health probe for OMDb, Wikipedia, or Wikidata. This is a recorded exception to Principle IV, taken for port parity: the Function App has no such probes and this slice is a port, not a design. The debt it carries has two distinct failure modes, both inherited from the Function App unchanged: (a) a MISSING `OpenMovieDb:Api-Key` throws `ArgumentNullException` in `OpenMovieDbAgent`'s constructor, which fails scoped DI resolution on the first chat turn that tries to resolve `ChatPlanner` and surfaces as a 503 via slice 003's generic error handler; (b) a PRESENT-BUT-REJECTED key (bad key, rate-limited, OMDb outage) is caught inside `GetMovieRatings`'s try/catch and returned as a `MovieRatingResult(IsSuccess: false, ErrorMessage: "Error: {ex.Message}")` tool payload, so the model receives the error, composes a graceful answer, and the chat turn still returns 200. The slice accepts both outcomes rather than launder them as Principle IV compliance. A follow-up slice may add the probes without touching this spec.
- **FR-016**: `FunnyFact` MUST remain absent from the structured-output `MovieListResponse` schema from slice 003 (slice 003's FR-013). The model MUST NOT be asked to produce a `FunnyFact`; the value in the envelope comes from the out-of-band ChatPlanner pipeline exclusively, matching the Function App.
- **FR-017**: `WikipediaSearchAgent.GetEnhancedInfo` MUST catch its own exceptions and return `null` on failure (the Function App's existing `catch (Exception ex) { logger.LogError(...); return null; }`), so neither a Wikipedia 403/404/5xx nor a Wikidata timeout escalates past the ChatPlanner tool boundary. Combined with FR-007's SafeGenerate catch, this means no Wikipedia/Wikidata outage MUST produce a non-200 chat response.
- **FR-018**: ChatPlanner's `GenerateEnhancedFunnyFact` MUST ONLY be invoked by the agent-turn pipeline (per FR-007), MUST NOT be registered as a tool, and MUST NOT appear in `CreateTools()`. Slice 003's single-agent tool list MUST remain exactly the ported TMDb kernel functions + ported DateTime kernel functions + the six tools listed in FR-001.

### Out of Scope *(explicitly excluded from this feature)*

- Custom telemetry: `Telemetry.cs`, `InstrumentedAIFunction`, per-tool duration/failure metrics, the `OpenTelemetryChatClient` wiring, cost/pricing emission, and any Application Insights log exporter. Slice 005 covers this. Tool invocations continue to be observable through whatever default tracing slice 003 already configures.
- Frontend changes, SDK updates, or OpenAPI client regeneration.
- Health probes for OMDb, Wikipedia, or Wikidata. The Function App has none; this slice carries the same gap as a recorded Principle IV exception for port parity (see FR-015 rationale, including the two distinct failure modes), to be revisited in a later slice.
- Changes to slice 003's TMDb hydration path, context reducer, structured-output schema, session persistence, Cosmos partition key, resilience pipeline, 404/503 error contract, or any slice 003 health probe.
- Any new entity types for Wikipedia/Wikidata beyond movie / actor / director.
- Exposing `WikipediaSearchAgent` directly to the model as a tool. The Function App does not; neither does this slice.
- `FunnyFact` as a property of the structured-output `MovieListResponse` schema (see FR-016).
- Caching of OMDb, Wikipedia, or Wikidata responses. The Function App performs none and this slice adds none.
- Changing the Function App's running `Chat-Ask`, `Chat-Ask-V2`, `Chat-Start`, or related endpoints.
- Any migration of OMDb-sourced rating snapshots into Cosmos. OMDb is fetched live per tool call, matching the Function App.
- Session concurrency control. Still none, same as slice 003.
- Deprecating or removing the committed OMDb key from the `movie-tracker-backend` repository (that is a separate repo; this slice only forbids its reuse in this one).

### Key Entities

- **ChatPlanner (ported from `Prompts/ChatPlanner.cs`)**: a scoped service holding a bare `IChatClient`, `WikipediaSearchAgent`, `OpenMovieDbAgent`, and `TrailerAgent`. Exposes `CreateTools()` returning the six tools in FR-001 plus the non-tool `GenerateEnhancedFunnyFact(string)` consumed by the agent-turn pipeline (FR-007).
- **OpenMovieDbAgent (ported from `Agents/OpenMovieDbAgent.cs`)**: a scoped service wrapping `AsyncOmdbClient`. Produces `MovieRatingResult` (with `Title`, `Year`, `ImdbRating`, `ImdbVotes`, `RottenTomatoesRating`, `MetacriticRating`, `BoxOffice`, `Rated`, `Runtime`, `Genre`, `Director`, `Writer`, `Actors`, `Awards`, `Plot`, `IsSuccess`, `ErrorMessage`, `Trailer`) and `RatingComparisonResult`.
- **TrailerAgent (ported from `Agents/TrailerAgent.cs`)**: a scoped service wrapping the slice 003 `TMDbClient` singleton. Produces the `[TRAILER]...[/TRAILER]` embed string in a JSON payload, or an error+hint JSON payload for unresolved titles and missing trailers.
- **WikipediaSearchAgent (ported from `Agents/WikipediaSearchAgent.cs`)**: a typed `HttpClient` service with the Wikimedia User-Agent and 15-second timeout. Produces `WikipediaResult` with `WikipediaContent` (summary + thumbnail), `WikidataInfo` (structured facts + related entities), and a `ConfidenceScore` in `[0.0, 1.0]`.
- **DetectedEntity (private record in ChatPlanner)**: `{ Name, Type }`, with `Type` normalised to `movie` / `actor` / `director` by `ParseDetectedEntity` (FR-010). `None` sentinel represents "no specific entity named by the user".
- **Chat session document (`MoviceTrackerChatSession`)**: slice 002's Cosmos document; this slice begins writing non-null values to its existing `FunnyFact` property. The property's shape, type, and placement in the document do not change.
- **Response envelope (`ChatMessageResponse` and `ChatTurnResponse`)**: slice 003's response types. Their `funnyFact` field - previously always null (slice 003's FR-004) - may now carry a non-empty string sourced from the session's `FunnyFact` (FR-011).
