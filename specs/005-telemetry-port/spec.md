## User Scenarios & Testing *(mandatory)*

### User Story 1 - Operator sees the same five custom instruments in App Insights for the API as they do for the Function App (Priority: P1)

An operator opens the Application Insights workspace the API Container App already writes to and runs the same custom-metric queries they run against the Function App. They see `gen_ai.client.tool.duration`, `gen_ai.client.tool.invocations`, `chat.turn.tool_calls`, `chat.context.retained_ratio`, and (when pricing is configured) `gen_ai.usage.cost_usd` emitted from the API's revision with the same instrument shape and dimensions.

**Why this priority**: The five custom instruments are the only metric surface the Function App uses to answer "which tools are failing," "how close is a turn to its iteration cap," "is compaction still saving anything," and "what is this costing." Without them the API's App Insights view is strictly worse than the Function App's for the same questions. P1 because this is the primary observable gap this slice exists to close.

**Independent Test**: Manual. After deploy, run a chat turn (`GET /api/chat/start` then `POST /api/chat/{chatId}/ask`) against the deployed revision with an input that exercises at least one tool (for example `"what's the IMDb rating of Inception?"`, exercising `GetMovieRating`). In Application Insights Logs, run `customMetrics | where cloud_RoleName == "movie-tracker-api" | summarize count() by name` and verify that `gen_ai.client.tool.duration`, `gen_ai.client.tool.invocations`, `chat.turn.tool_calls`, and `chat.context.retained_ratio` all appear. Run the same query against the Function App's role name and confirm the same four instrument names appear (plus `gen_ai.usage.cost_usd` when `AzureOpenAI:Price-Input-Per-1M` / `Price-Output-Per-1M` are configured on either side).

**Acceptance Scenarios**:

1. **Given** the API's deployed revision has processed at least one chat turn that invoked a tool, **When** the operator queries `customMetrics` filtered on the API's role name, **Then** `gen_ai.client.tool.duration` and `gen_ai.client.tool.invocations` appear with the two dimensions `gen_ai.tool.name` (the tool's `Name`) and `outcome` (`"ok"` or `"error"`), matching the Function App's shape (FR-004).
2. **Given** the API has processed at least one chat turn, **When** the operator queries `customMetrics` for `chat.turn.tool_calls`, **Then** the metric appears with the integer count of `FunctionCallContent` items emitted during the turn, same shape as the Function App (FR-004).
3. **Given** the API has processed at least one chat turn whose stored history was non-empty before the turn, **When** the operator queries `customMetrics` for `chat.context.retained_ratio`, **Then** the metric appears as a dimensionless ratio of `modelMessages.Count / chatMessages.Count` (FR-004).
4. **Given** the API has `AzureOpenAI:Price-Input-Per-1M` and `AzureOpenAI:Price-Output-Per-1M` configured, **When** the operator queries `customMetrics` for `gen_ai.usage.cost_usd`, **Then** the metric appears with a `gen_ai.request.model` dimension carrying the deployment name, and cached-input tokens are billed at the cached rate when `AzureOpenAI:Price-Cached-Input-Per-1M` is also present (FR-004, FR-009).
5. **Given** the API has `AzureOpenAI:Price-*` entries absent, **When** the operator queries `customMetrics` for `gen_ai.usage.cost_usd`, **Then** no `gen_ai.usage.cost_usd` records appear at all (the Function App's "unconfigured, nothing emitted" behaviour; FR-009).

### User Story 2 - Operator can trace a chat turn end-to-end for the API in App Insights (Priority: P1)

An operator opens the Application Insights Transaction search for a `chatId` that just ran a turn against the API. They see a dependency / request graph that includes (a) the API's hand-rolled endpoint span (`movie-tracker-api.chat-start`, `movie-tracker-api.chat-ask`, or `movie-tracker-api.chat-ask-v2`), (b) the framework's `chat` and `orchestrate_tools` spans emitted by `OpenTelemetryChatClient`, (c) one `execute_tool <name>` span per tool call, (d) the hand-rolled Cosmos spans (`movie-tracker-api.chat-session-repository.new-chat-session` / `.get-chat-session` / `.save-chat-session`), (e) the token-usage tags (`gen_ai.usage.input_tokens`, `gen_ai.usage.output_tokens`, `gen_ai.usage.cache_read.input_tokens`, `gen_ai.usage.reasoning.output_tokens`) attached to the enclosing endpoint span, and (f) ASP.NET Core request spans and outgoing HttpClient dependency spans around TMDb / OMDb / OpenAI / Wikipedia / Wikidata. This is the same trace shape the Function App produces for the equivalent request.

**Why this priority**: Traces are how an operator answers "what happened on this one request." Without the hand-rolled endpoint and repository spans and the token-usage tags, the API's App Insights trace is strictly less informative than the Function App's for the same investigation. P1 because this is the second half of the primary observable gap this slice closes.

**Independent Test**: Manual. Create a `chatId` against the deployed API revision, run one `POST /api/chat/{chatId}/ask` with an input that calls at least one tool, and in Application Insights Transaction search locate the operation for that request. Verify the trace tree contains (a) one `movie-tracker-api.chat-ask` span at the top (not `movie-tracker-func.*`), (b) at least one `chat` span under it (when the model's `UsageDetails` carried an `InputTokenCount`, `gen_ai.usage.input_tokens` is tagged on the parent endpoint span; a null count is correctly untagged), (c) at least one `execute_tool <name>` span for the tool that ran, (d) a `movie-tracker-api.chat-session-repository.save-chat-session` span, and (e) an outgoing HttpClient dependency on `api.themoviedb.org` or `www.omdbapi.com`. Repeat against the Function App's `Chat-Ask` endpoint and visually confirm the same span classes are present.

**Acceptance Scenarios**:

1. **Given** a chat turn ran on the API, **When** the operator opens its transaction in App Insights, **Then** the trace includes a span named `movie-tracker-api.chat-ask` (or `.chat-start` / `.chat-ask-v2` for those routes), produced by an ActivitySource whose name equals the API's service name (FR-007).
2. **Given** a chat turn ran on the API and the model call returned a non-null `UsageDetails`, **When** the operator inspects the endpoint span, **Then** the `gen_ai.usage.*` tags corresponding to the non-null fields on that `UsageDetails` are set on the enclosing `Activity.Current` (null fields are not tagged; a null `Activity.Current` is a no-op, matching `Activity.Current?.SetTag` in the Function App) (FR-007).
3. **Given** a chat turn ran on the API that invoked at least one tool, **When** the operator inspects the trace, **Then** the framework spans `chat`, `orchestrate_tools`, and one `execute_tool <name>` per invoked tool are present under the endpoint span - emitted because `UseOpenTelemetry(..., serviceName, ...)` is applied to the chat client and the `TracerProvider` has `AddSource(serviceName)` (FR-002). A turn that invokes no tools MUST still carry the endpoint span and at least one `chat` span.
4. **Given** a session create or save ran against Cosmos, **When** the operator inspects the trace, **Then** a `movie-tracker-api.chat-session-repository.new-chat-session` / `.get-chat-session` / `.save-chat-session` span is present (FR-007).
5. **Given** an HTTP request reached the API, **When** the operator opens the transaction, **Then** the ASP.NET Core request span and any outgoing HttpClient dependency spans are visible, same shape as the Function App's `AddAspNetCoreInstrumentation` + `AddHttpClientInstrumentation` output (FR-002).

### User Story 3 - Application logs reach App Insights for the API, with trace-based log sampling disabled (Priority: P2)

An operator investigates a 503 or a server-side error on the API. The `LogCritical`, `LogError`, and `LogInformation` calls emitted during the failing or succeeding turn appear in Application Insights `traces` / `exceptions` tables. The `AzureMonitorLogExporter` is registered with `EnableTraceBasedLogsSampler = false` so that log retention does not inherit the trace-sampling decision - the knob the Function App's `Program.cs:99-111` comment identifies as the fix that made application logs reach App Insights at all.

**Why this priority**: Without the Function App's log-exporter wiring, application-category logs are the "silent swallow" bug the Function App had to fix. P2 rather than P1 because the trace surface in US2 is still useful on its own; this story's remit is matching the Function App's log-pipeline shape, not independently proving sampling behaviour against the live backend (which is Azure Monitor's responsibility, not this slice's).

**Independent Test**: Manual. Trigger a known-failing path on the deployed API revision (for example, call `POST /api/chat/{chatId}/ask` with a `chatId` the repository will not find, causing the 404 branch to log; or hit a path that invokes `ChatPlanner` under a missing config key and triggers `LogCritical` in the generic error handler). In App Insights, query `traces | where cloud_RoleName == "movie-tracker-api" and severityLevel >= 2 | project timestamp, message, operation_Id` and verify the log line appears. Repeat with a successful chat turn and verify the `LogInformation` lines (`Chat-Ask usage: ...`, `Chat-Ask context: sending ... of ... stored messages`) also appear in `traces` at severity Information. A code review MUST confirm `EnableTraceBasedLogsSampler = false` is set at the single exporter registration site.

**Acceptance Scenarios**:

1. **Given** the API logs a `LogCritical` or `LogError` from inside an endpoint handler, **When** the operator queries `traces` or `exceptions`, **Then** the entry is present with the fully formatted message (not `{Placeholder}` tokens) and with the Functions-style scope data if any was attached, matching the Function App's `IncludeFormattedMessage = true` and `IncludeScopes = true` (FR-003).
2. **Given** the `AzureMonitorLogExporter` is registered on the host's logging builder, **When** a code review inspects the single registration site, **Then** `EnableTraceBasedLogsSampler = false` is set, matching the Function App (FR-003).
3. **Given** the API logs structured messages with `{InputTokens}`, `{CachedInputTokens}`, `{OutputTokens}`, `{ReasoningTokens}`, `{TotalTokens}`, `{IncludedMessages}`, `{TotalMessages}`, `{ChatId}`, `{Count}`, `{Limit}`, `{ToolName}`, `{ToolArguments}`, `{ElapsedMs}`, `{Error}`, **When** the operator reads those entries in App Insights, **Then** each property is available as a `customDimensions` key with the Function App's exact property name (FR-005, FR-008).

### User Story 4 - Operator can toggle sensitive-data telemetry on the API with the same config switch the Function App uses (Priority: P3)

An operator sets `Telemetry:Enable-Sensitive-Data` to `false` on the API's Container App (either as an env var `Telemetry__Enable-Sensitive-Data=false` or as a deployed secret value), restarts the revision, and verifies that (a) `OpenTelemetryChatClient` no longer records prompts and completions on its `chat` spans, and (b) `InstrumentedAIFunction` renders `"(arguments not logged)"` in place of the tool arguments in its structured log line. With the key unset or set to `true`, both continue to carry the user's names/titles, matching the Function App's defaults.

**Why this priority**: The switch has one legitimate use (handling data that should not land in telemetry) and is otherwise left at its `true` default. P3 because it is a knob, not a surface - no caller depends on it being observable - but the port must carry it or the gate becomes a one-way door at compile time.

**Independent Test**: Manual. Deploy the API with `Telemetry:Enable-Sensitive-Data` unset (default) and run a chat turn with a tool call; in App Insights verify the `execute_tool` span's `gen_ai.tool.call.arguments` attribute (or equivalent) contains the model's argument values, and the `tool ... ok in ...ms` log line contains the real arguments after the tool name. Redeploy with `Telemetry__Enable-Sensitive-Data=false`, run the same request, and verify the arguments are absent from both the span attribute and the log line (the log line reads `(arguments not logged)`).

**Acceptance Scenarios**:

1. **Given** `Telemetry:Enable-Sensitive-Data` is unset, **When** a tool runs, **Then** the chat client records prompts and completions on its spans (framework default when `EnableSensitiveData = true`) and the `InstrumentedAIFunction` log line carries the rendered arguments (FR-006).
2. **Given** `Telemetry:Enable-Sensitive-Data=false`, **When** a tool runs, **Then** the chat client omits prompts and completions on its spans and the `InstrumentedAIFunction` log line reads `(arguments not logged)` (FR-006).
3. **Given** either value, **When** the metric records fire, **Then** neither `gen_ai.client.tool.duration`, `gen_ai.client.tool.invocations`, `chat.turn.tool_calls`, `chat.context.retained_ratio`, nor `gen_ai.usage.cost_usd` carries user input as a dimension (the switch has no effect on metrics; FR-004).

### Edge Cases

- **`APPLICATIONINSIGHTS_CONNECTION_STRING` is unset in the running container**: The port MUST NOT add application-level startup validation of the connection string - the Function App itself does not validate its App Setting at startup, so the port keeps that same unvalidated-startup behaviour. No fallback value, no exception-swallowing wrapper, no probe is introduced. What the three exporters do with a null `ConnectionString` is Azure Monitor's responsibility; this slice makes no claim about it.
- **A tool throws**: `InstrumentedAIFunction.InvokeCoreAsync` records `outcome=error` on the two tool instruments and rethrows. The framework's `execute_tool <name>` span catches it, records `ActivityStatusCode.Error`, and hands the model a correctable error payload. Chat turn still returns 200 if the model can recover; otherwise slice 003's generic 503 handler fires and `LogCritical` writes an entry.
- **A chat turn runs with an empty stored history** (`chatMessages.Count == 0`): `chat.context.retained_ratio` is NOT recorded (the Function App guards this with `if (chatMessages.Count > 0)`; the port keeps that guard - dividing by zero would push bad data into the histogram).
- **Only `AzureOpenAI:Price-Input-Per-1M` is configured, not `Price-Output-Per-1M`**: `ModelPricing` is `null` (both inputs/outputs are required by the ternary at `Function.cs:212-218`), so `gen_ai.usage.cost_usd` emits nothing. Partial pricing is the "unconfigured" state, not "half-priced."
- **`AzureOpenAI:Price-Cached-Input-Per-1M` is unset but input/output are set**: Cached input is billed at the uncached rate (`pricing.CachedInputPerMillion ?? pricing.InputPerMillion`), understating the discount rather than overstating cost. Matches the Function App.
- **Adaptive sampling drops a `chat` span**: `gen_ai.client.token.usage` and `gen_ai.client.operation.duration` histograms still emit from the framework's `OpenTelemetryChatClient` (metrics are not sampled); the span's inline token count is lost on this call but totals remain accurate. This is the whole reason the framework-emitted metrics path exists; the port MUST NOT disable the framework's metric emission to compensate.
- **`UsageDetails` is `null` on an `AgentResponse`** (model path returned no usage): The port's `LogUsage` equivalent returns early; `Activity.Current` tags are not set, `gen_ai.usage.cost_usd` is not recorded. Matching the Function App's `if (result.Usage is not { } usage) return;` guard.
- **ASP.NET Core request pipeline logs a framework warning** (`Microsoft.AspNetCore.*` at `Warning` and above per `appsettings.json`): It MUST continue to flow to App Insights, because the OTel logging pipeline is attached to the host's `ILoggerFactory` and all providers see all records that pass their filters. The port MUST NOT silence framework categories while porting application-category wiring.
- **A tool argument is longer than 120 characters**: `InstrumentedAIFunction.Render` truncates to 120 chars plus `"..."`. Matches the Function App's `MaxLoggedArgumentChars = 120`.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: `MovieTracker.Api.csproj` MUST add the three telemetry NuGet packages the Function App uses that have an ASP.NET Core equivalent: `Azure.Monitor.OpenTelemetry.AspNetCore` (`1.6.0`), `Azure.Monitor.OpenTelemetry.Exporter` (`1.8.3`), and `OpenTelemetry.Extensions.Hosting` (`1.17.0`). The Function App's `Microsoft.ApplicationInsights.WorkerService` and both `Microsoft.Azure.Functions.Worker.*` packages are Worker-specific and MUST NOT be added. If the ASP.NET Core generic-host OTel helpers are already pulled in transitively by `Azure.Monitor.OpenTelemetry.AspNetCore`, the explicit `OpenTelemetry.Extensions.Hosting` reference MAY be omitted; the implementation plan will confirm.

- **FR-002**: `MovieTracker.Api/Program.cs` MUST wire OpenTelemetry via `services.AddOpenTelemetry()` with two builders registered in this order and with these exact contents, matching `movie-tracker-backend/src/MovieTracker.Backend/Program.cs:332-368`:
  1. `.WithTracing(builder => ...)` adds **five** `ActivitySource`s - `serviceName`, `"Microsoft.Extensions.AI*"`, `"Microsoft.Agents.AI*"`, `"Azure.AI.OpenAI*"`, `"OpenAI*"` - sets the resource builder to `ResourceBuilder.CreateDefault().AddService(serviceName, serviceVersion)`, adds `AddAspNetCoreInstrumentation()` and `AddHttpClientInstrumentation()`, and adds `AddAzureMonitorTraceExporter(options => options.ConnectionString = ...)` sourced from the config read in FR-010.
  2. `.WithMetrics(builder => ...)` adds `AddMeter(serviceName)`, sets the same resource builder, adds `AddHttpClientInstrumentation()`, and adds `AddAzureMonitorMetricExporter(options => options.ConnectionString = ...)`.

  No `.WithLogging(...)` call MUST be made on this builder - the Function App explicitly rejects that path with a code comment (`Program.cs:369-373`) because "no MovieTracker.* category has ever appeared in App Insights" with the exporter attached there. Logs are wired separately per FR-003. The ASP.NET Core-specific one-stop `services.AddAzureMonitor()` call from the distro is NOT used; the port keeps the Function App's explicit-exporter shape.

- **FR-003**: `MovieTracker.Api/Program.cs` MUST attach the Azure Monitor log exporter to the host's logging builder via `builder.Logging.AddOpenTelemetry(options => ...)` (ASP.NET Core's generic-host logging builder is the equivalent of the Function App's `ConfigureLogging` registration site). The configuration MUST set `IncludeFormattedMessage = true`, `IncludeScopes = true`, the same resource builder as FR-002, and `AddAzureMonitorLogExporter(exporter => { exporter.ConnectionString = ...; exporter.EnableTraceBasedLogsSampler = false; })`. Both `IncludeFormattedMessage` and `EnableTraceBasedLogsSampler = false` are load-bearing per the Function App's `Program.cs:86-112` comments; omitting either reproduces the "silent swallow" bug the Function App had to fix.

- **FR-004**: `MovieTracker.Api` MUST introduce a `Telemetry` static class (ported from `movie-tracker-backend/src/MovieTracker.Backend/Telemetry.cs`, behaviour-preserving) exposing a single `Meter` and the five instruments below with the Function App's exact names, units, descriptions, and dimensions:
  1. `Histogram<double> ToolDuration` - `"gen_ai.client.tool.duration"`, unit `"s"`, dimensions `gen_ai.tool.name` (tool `Name`) and `outcome` (`"ok"` / `"error"`).
  2. `Counter<long> ToolInvocations` - `"gen_ai.client.tool.invocations"`, unit `"{invocation}"`, same two dimensions.
  3. `Histogram<int> ToolCallsPerTurn` - `"chat.turn.tool_calls"`, unit `"{call}"`, no dimensions.
  4. `Histogram<double> ContextRetainedRatio` - `"chat.context.retained_ratio"`, unit `"1"`, no dimensions.
  5. `Counter<double> CostUsd` - `"gen_ai.usage.cost_usd"`, unit `"USD"`, dimension `gen_ai.request.model`.

  The `Meter` MUST be named with the API's `serviceName` (see FR-010) and versioned with `serviceVersion`. The static `RecordTool(toolName, elapsed, succeeded)` and `RecordCost(model, usage, pricing)` helper methods MUST be ported behaviour-preserving - including `RecordCost`'s cached-input split (`cachedInput = usage.CachedInputTokenCount ?? 0; freshInput = max(0, InputTokenCount - cachedInput); cost = fresh/1M * Input + cached/1M * (Cached ?? Input) + Output/1M * Output`) and the `if (cost > 0)` guard. The accompanying `ModelPricing` record MUST be ported with the three fields (`InputPerMillion`, `OutputPerMillion`, `CachedInputPerMillion?`) in that order. Per the project's coding standards, the port MUST NOT carry forward inline comments or single-line `if` statements without braces from the source. File layout is an implementation detail left to `plan.md`.

- **FR-005**: `MovieTracker.Api` MUST introduce an `InstrumentedAIFunction` sealed class (ported from `Telemetry.cs:143-223`) deriving from `DelegatingAIFunction`. Its `InvokeCoreAsync` MUST (a) start a `Stopwatch`, (b) `await base.InvokeCoreAsync`, (c) on success call `Telemetry.RecordTool(Name, elapsed, succeeded: true)` and `LogCall(arguments, elapsed, error: null)`, (d) on exception call `Telemetry.RecordTool(Name, elapsed, succeeded: false)` and `LogCall(arguments, elapsed, ex)` and rethrow untouched. `LogCall` MUST honour an injected `ILogger`, early-return if the logger is null or `IsEnabled(Information)` is false, render arguments via a `Render` helper behaviourally equivalent to the Function App's (join `key=value` pairs, truncate values beyond 120 characters with `"..."`, skip nulls), and emit either `LogInformation("tool {ToolName}({ToolArguments}) ok in {ElapsedMs}ms", ...)` on success or `LogWarning("tool {ToolName}({ToolArguments}) FAILED in {ElapsedMs}ms: {Error}", ...)` on failure. Argument rendering MUST be gated on the `logArguments` constructor flag (`"(arguments not logged)"` when false). `MaxLoggedArgumentChars = 120` MUST be preserved. Per the project's coding standards, the port's `Render` MUST use braces on every `if` even single-line and MUST NOT copy forward the source's inline comments; the behavioural contract above is the parity bar.

- **FR-006**: `Program.cs` MUST read `Telemetry:Enable-Sensitive-Data` as a nullable `bool` (default `true`) ONCE at startup and feed it into:
  1. `IChatClient` registration: `.UseOpenTelemetry(loggerFactory, serviceName, options => options.EnableSensitiveData = enableSensitiveTelemetry)` applied to the chat client before `.Build(sp)`, matching `Program.cs:272`.
  2. `AIAgent` registration: before building the agent, each `AIFunction` in the agent's tool list is wrapped in `new InstrumentedAIFunction(function, toolLogger, enableSensitiveTelemetry)`, with `toolLogger` created from the service provider's `ILoggerFactory` under the category `"MovieTracker.Api.ToolCalls"` (the Function App uses `"MovieTracker.Backend.ToolCalls"` - the category name is updated to the API's assembly namespace; the shape and purpose are unchanged).

  `.UseOpenTelemetry` MUST be applied only to the chat client, NOT to the agent, matching `Program.cs:248-255`'s "stacking the two records `gen_ai.client.token.usage` twice per model call" rationale. `AIAgentBuilder.UseOpenTelemetry` MUST NOT be added.

- **FR-007**: The agent-turn pipeline (slice 003's `ChatTurnEndpoints.Ask` / `AskV2` and `/api/chat/start` handler, plus `ChatSessionRepository`) MUST emit the following hand-rolled spans and tags, ported from `Functions/Function.cs:387, 854, 906, 728-732` and `ChatSessionRepository.cs:57, 82, 100`:
  1. The `/api/chat/start` handler MUST open `tracer.StartActiveSpan("movie-tracker-api.chat-start")` for the duration of the handler. (The Function App's prefix `movie-tracker-func` becomes `movie-tracker-api` because it reads as the span's owning service in App Insights.)
  2. The `/api/chat/{chatId}/ask` handler MUST open `"movie-tracker-api.chat-ask"`; `/api/chat/{chatId}/ask/v2` MUST open `"movie-tracker-api.chat-ask-v2"`.
  3. The RunTurn logic MUST read `Activity.Current` after the model call returns and - when the response carries a non-null `UsageDetails` - set four tags on it: `gen_ai.usage.input_tokens` (`usage.InputTokenCount`), `gen_ai.usage.output_tokens` (`usage.OutputTokenCount`), `gen_ai.usage.cache_read.input_tokens` (`usage.CachedInputTokenCount`), `gen_ai.usage.reasoning.output_tokens` (`usage.ReasoningTokenCount`). This MUST be done through `Activity.Current?.SetTag(...)` so a null `Activity.Current` is a no-op, as in the Function App.
  4. `ChatSessionRepository`'s three methods MUST open `"movie-tracker-api.chat-session-repository.new-chat-session"`, `".get-chat-session"`, and `".save-chat-session"` respectively.

  The spans MUST be opened on the `Tracer` registered as a singleton via `services.AddSingleton(TracerProvider.Default.GetTracer(serviceName, serviceVersion))` (matching `Program.cs:148`). This is the same `Tracer` the Function App uses; the port keeps that one-liner registration.

- **FR-008**: The agent-turn pipeline MUST emit the following structured log calls the Function App emits at the equivalent sites, with the Function App's exact message templates and property names:
  1. After the model call, when `AgentResponse.Usage` is non-null: `logger.LogInformation("Chat-Ask usage: input={InputTokens} cachedInput={CachedInputTokens} output={OutputTokens} reasoning={ReasoningTokens} total={TotalTokens}", ...)` (ported from `Function.cs:718-724`).
  2. Before the model call: `logger.LogInformation("Chat-Ask context: sending {IncludedMessages} of {TotalMessages} stored messages to the model", ...)` (ported from `Function.cs:808-810`).
  3. In the hydration trim path (if slice 003's hydration cache is replayed): `logger.LogInformation("Hydration cache for session {ChatId} holds {Count} movies; trimming to {Limit}", ...)` (ported from `Function.cs:751-753`). This line fires only when the port's equivalent code path exists and trips the limit; if slice 003 did not import that path, this bullet is a no-op and MUST NOT be invented.
  4. Three `LogCritical("{@ex}", ex)` calls in the catch arms of `ChatSessionRepository.NewChatSession` / `GetChatSession` / `SaveChatSession`, ported from `ChatSessionRepository.cs:75, 90, 108`. The `{@ex}` capturing operator MUST be preserved so the structured exception object reaches App Insights.

  Message templates are the Function App's verbatim; the `"Chat-Ask"` prefix is kept as-is (it names the operation class, not the exact function name).

- **FR-009**: `Program.cs` MUST read `AzureOpenAI:Price-Input-Per-1M`, `AzureOpenAI:Price-Output-Per-1M`, and `AzureOpenAI:Price-Cached-Input-Per-1M` using `double.TryParse` against `IConfiguration`, assembling a `ModelPricing` record ONLY when `Input` and `Output` both parse; otherwise `modelPricing` is `null`. The resulting `ModelPricing?` MUST reach the agent-turn pipeline (via DI or captured field) and the pipeline MUST call `Telemetry.RecordCost(deployedModel, usage, pricing)` after the model call when `modelPricing is { } pricing` and the response carries a `UsageDetails`. `deployedModel` MUST be the configured deployment name (slice 003's `AzureOpenAI:DeploymentName`). The Function App's config key names (`AzureOpenAi:*` with lowercase `i`) are updated to the API's existing casing convention (`AzureOpenAI:*` with uppercase `I`), consistent with slice 003's existing keys; the Function App's values and semantics are unchanged.

- **FR-010**: The `serviceName` constant MUST equal `"movie-tracker-api"` (the Function App uses `"movie-tracker-backend"`; the port updates to the API's name since it names the role `cloud_RoleName` in App Insights). `serviceVersion` MUST equal `"1.0.0"`, matching the Function App's `Telemetry.ServiceVersion`. Both values MUST live on the ported `Telemetry` static class as the single source of truth (`Telemetry.SourceName`, `Telemetry.ServiceVersion`). The same `serviceName` MUST be the `sourceName` argument to `.UseOpenTelemetry` on the chat client (FR-006), the argument to `AddSource` and `AddMeter` on the OTel builders (FR-002), and the `AddService(serviceName, serviceVersion)` argument on the resource builder - the Function App's `Program.cs:28-33` and `Telemetry.cs:36-42` comments explain this is load-bearing. The connection string MUST be read via `builder.Configuration["APPLICATIONINSIGHTS_CONNECTION_STRING"]` (underscore form - this is the standard ASP.NET Core env-var mapping already set by `infrastructure/container-app.bicep:52-54`; the Function App uses the hyphen form `APPLICATIONINSIGHTS-CONNECTION-STRING` because Azure Functions historically prefers that spelling, but the Container App revision env var in this repo is underscore-only). The value feeds all three exporters (traces, metrics, logs).

- **FR-011**: `host.json`-style sampling is Function-App-specific and has no direct ASP.NET Core equivalent. The port MUST NOT introduce a custom `Sampler` on the TracerProviderBuilder. The Azure Monitor OpenTelemetry Exporter applies its own ingestion sampling and the operator can tune it via Application Insights' built-in ingestion sampling / adaptive sampling at the resource level (no code change needed). The Function App's `host.json` `excludedTypes: "Request"` carve-out and `enableLiveMetricsFilters: true` toggle do NOT port into code; both are Function-host configuration surfaces that the Container App has no equivalent for. The decoupling of log retention from trace sampling - the one knob that matters at code level - is already covered by `EnableTraceBasedLogsSampler = false` in FR-003.

- **FR-012**: `appsettings.json` MUST add an `OpenTelemetry` subsection under `Logging` mirroring the Function App's (`appsettings.json:6-10`):

  ```json
  "Logging": {
    "LogLevel": { ... },
    "OpenTelemetry": {
      "IncludeFormattedMessage": true,
      "IncludeScopes": true,
      "ParseStateValues": true
    }
  }
  ```

  These three flags MUST be applied by the FR-003 `AddOpenTelemetry` logging configuration via the standard `Logging:OpenTelemetry:*` binding path (which the OTel `AddOpenTelemetry` registration honours by default). The log-level section slice 003 already uses (`"Default": "Information"`, `"Microsoft.AspNetCore": "Warning"`) MUST be preserved.

- **FR-013**: No new Azure resources MUST be added to Bicep. The existing `infrastructure/main.bicep` already provisions the Log Analytics workspace (`logAnalytics`, `Microsoft.OperationalInsights/workspaces@2023-09-01`, SKU `PerGB2018`, 30-day retention), the Application Insights component (`appInsights`, `Microsoft.Insights/components@2020-02-02`, workspace-backed, 30-day retention), the Container App Environment with Log Analytics linked, and the `APPLICATIONINSIGHTS_CONNECTION_STRING` env var in `infrastructure/container-app.bicep:52-54`. This slice MUST NOT change SKUs, retention days, daily quotas, public-network-access toggles, workspace linkage, or any other property of these resources. The Function App's bicep writes the connection string into Key Vault as a separate secret; the API's bicep already surfaces the connection string directly on the Container App as an env var, which is the ASP.NET Core-standard pattern, so no Key Vault secret resource is added for telemetry.

- **FR-014**: `Program.cs` MUST NOT add application-level startup validation for `APPLICATIONINSIGHTS_CONNECTION_STRING`. The Function App does not validate its App Setting at startup, and the port keeps that behaviour. No fallback value, no exception-swallowing wrapper, no probe is introduced. The slice-003 pattern of validating only resource-plane configuration (Cosmos / AzureOpenAI / TMDb) at the top of `Program.cs` is preserved. The behaviour of the three Azure Monitor exporters when their `ConnectionString` is null is Azure Monitor's responsibility and is not under test here.

- **New metrics**. No instruments beyond the five in FR-004 are added. In particular, no HTTP latency histogram, no Cosmos operation histogram, no `health` probe counter, no OMDb/TMDb/Wikipedia dependency metrics, no per-endpoint request counter. - **`Microsoft.ApplicationInsights.*` SDK (the "classic" 2.x API)** including `TelemetryClient`, `TrackEvent`, `TrackMetric`, `TrackDependency`, `TrackException`, `TrackTrace`, `TrackRequest`, `ITelemetryInitializer`, `ITelemetryProcessor`, or any `TelemetryConfiguration` manipulation.
