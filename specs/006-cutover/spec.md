## User Scenarios & Testing *(mandatory)*

### User Story 1 - The deployed Static Web App drives chat against the Container App end to end (Priority: P1)

A user loads the production Static Web App at `https://green-mud-037bbdc1e.5.azurestaticapps.net`, opens the chat UI, and runs a complete chat exchange (start a session, send a message, see the model's response, send a follow-up on the same `chatId`, see the follow-up response). Every request the browser issues to the chat API lands on the Container App at `https://movie-tracker-api.politeocean-1c0085f8.westus3.azurecontainerapps.io`, and no request lands on the Function App.

**Why this priority**: The whole point of the cutover is to retire the Function App as the frontend's backend. Until the deployed SWA actually drives traffic to the Container App for a full chat flow, nothing else in this slice is safe to do (CORS tightening and the Function App stop both assume this works). P1 because this is the migration itself; the other two stories are the operational wrap-around that make the cutover complete.

**Independent Test**: Manual. After the frontend's API base URL change is deployed to the Static Web App, open the production SWA URL in a browser with DevTools' Network tab open. Start a new chat (observe one request to `.../api/chat/start` on the Container App host, 200 response with a `chatId`). Send a chat message and observe the `.../api/chat/{chatId}/ask` request on the Container App host return 200 with a non-empty model response rendered in the UI. Confirm the request's host in Network is the Container App FQDN, not `yh5ax4ws5lr3k-func-movie-tracker.azurewebsites.net`. Send one additional follow-up to confirm `chatId` continuity on the Container App. Both exchanges must succeed before User Story 3 begins. (Slice 004 already covers tool-execution correctness; the cutover does not re-prove it.)

**Acceptance Scenarios**:

1. **Given** the frontend has been redeployed with the updated `chatBaseUrl`, **When** a user loads the SWA and starts a chat from the UI, **Then** DevTools' Network tab shows the `start` request going to `movie-tracker-api.politeocean-1c0085f8.westus3.azurecontainerapps.io` and the response is a 200 with a non-empty `chatId` (FR-001).
2. **Given** a chat session exists, **When** the user sends a message, **Then** the `ask` request lands on the same Container App host, returns 200, and the UI renders a non-empty model response (FR-001).
3. **Given** the frontend has been redeployed, **When** DevTools' Network tab is inspected for any chat traffic over a complete session, **Then** zero requests target `yh5ax4ws5lr3k-func-movie-tracker.azurewebsites.net` (FR-001).

### User Story 2 - The chat API only accepts cross-origin browser calls from the Function App's historical origin set (Priority: P2)

A browser running code served from `https://green-mud-037bbdc1e.5.azurestaticapps.net` can call the chat API; a browser running code served from `http://localhost:4200` (Angular's default `ng serve` port, the Function App's historical local-dev origin) can also call the chat API; a browser running code served from any other origin (a Postman browser-mode request, an arbitrary other site) is blocked by the API's CORS policy. The wildcard `*` currently in the Container App ingress CORS allowlist is replaced with the Function App's historical origin set: `['https://green-mud-037bbdc1e.5.azurestaticapps.net', 'http://localhost:4200']`.

**Why this priority**: Wildcard CORS turns the public API into something any origin's browser code can call on behalf of a logged-in user. Locking the allowed origin list to the Function App's historical origin set is "parity, nothing more" — the production SWA host and the Angular `ng serve` dev origin that the Function App supported, and no other new or wildcard origin. P2 because User Story 1 can be verified while CORS is still wildcard; US2 is the hardening step that this slice must not skip but doesn't block US1's happy-path demo.

**Independent Test**: Manual. From a terminal, send a preflight to the Container App chat endpoint using `curl -i -X OPTIONS -H "Origin: https://green-mud-037bbdc1e.5.azurestaticapps.net" -H "Access-Control-Request-Method: POST" <container-app-url>/api/chat/start` and verify the response includes `Access-Control-Allow-Origin: https://green-mud-037bbdc1e.5.azurestaticapps.net` (echoing the exact origin, not `*`). Repeat with `-H "Origin: http://localhost:4200"` and verify the response echoes that origin. Repeat with `-H "Origin: https://evil.example.com"` and verify the response does **not** include an `Access-Control-Allow-Origin` header for that origin (the browser's preflight check would therefore fail). Then re-run User Story 1's independent test from the SWA to confirm the real browser flow is not broken by the tightened policy.

**Acceptance Scenarios**:

1. **Given** the Container App ingress CORS policy has been tightened, **When** a preflight is sent with `Origin: https://green-mud-037bbdc1e.5.azurestaticapps.net`, **Then** the response's `Access-Control-Allow-Origin` header exactly equals that origin (FR-003).
2. **Given** the Container App ingress CORS policy has been tightened, **When** a preflight is sent with `Origin: http://localhost:4200`, **Then** the response's `Access-Control-Allow-Origin` header exactly equals that origin (FR-003).
3. **Given** the Container App ingress CORS policy has been tightened, **When** a preflight is sent with any other origin, **Then** the response does not grant that origin access (`Access-Control-Allow-Origin` is absent or does not match the requested origin) (FR-003).
4. **Given** CORS is tightened, **When** User Story 1's end-to-end chat flow is re-run from the deployed SWA, **Then** every chat request still returns 200 and the UI still renders model responses (FR-003).
5. **Given** a code review of `infrastructure/container-app.bicep` after this slice, **When** the reviewer inspects the ingress `corsPolicy.allowedOrigins`, **Then** the list contains exactly the two Function-App-parity entries and no `*` (FR-004).

### User Story 3 - The Function App is stopped so no stale traffic can reach it (Priority: P3)

After User Stories 1 and 2 are verified end to end, an operator stops the Function App `yh5ax4ws5lr3k-func-movie-tracker` so that any stale client, bookmarked URL, or forgotten integration pointing at `https://yh5ax4ws5lr3k-func-movie-tracker.azurewebsites.net` fails fast instead of silently returning data from a parallel backend. The Function App is **stopped**, not deleted: it, its App Settings, its Key Vault secrets, and its deployment slot stay intact so the stop is reversible with a single click.

**Why this priority**: Leaving the Function App running after cutover is cheap on invocations (zero traffic) but expensive on operational clarity: two apparently-live backends silently diverge, and the next on-call engineer has no way to tell which is "real." P3 because the cutover is already functionally complete after US1 (frontend uses Container App) and already secure after US2 (CORS locked). Stopping the Function App is the cleanup that gets this slice to "no parallel backend" rather than "cutover done, old thing still humming."

**Independent Test**: Manual, performed only after US1 and US2 pass. The operator first resolves the hosting subscription and resource group for `yh5ax4ws5lr3k-func-movie-tracker` by running an authenticated search across the subscriptions they can see (for example `az resource list --name yh5ax4ws5lr3k-func-movie-tracker --resource-type Microsoft.Web/sites` under each configured `AZURE_CONFIG_DIR`, or an `az graph query` across tenants). With the resolved `--subscription` and `--resource-group`, the operator confirms the Function App's state is `Running` (`az functionapp show --name yh5ax4ws5lr3k-func-movie-tracker --query state`), then runs `az functionapp stop ...` with the same resolved scope. The operator confirms the state is now `Stopped` and that an HTTPS request to `https://yh5ax4ws5lr3k-func-movie-tracker.azurewebsites.net/api/chat/start` no longer returns a `chatId` (expected 403, 503, or connection error, depending on how Azure signals a stopped Function App). The operator re-runs User Story 1's test to confirm the SWA still works end to end. The Function App resource itself still exists in the resource group with its App Settings intact. If the Function App cannot be located in any accessible subscription after a deliberate resolution attempt, the operator records the resolution outcome and surfaces it to the slice owner rather than treating "not found" as "already stopped."

**Acceptance Scenarios**:

1. **Given** User Stories 1 and 2 are verified, **When** the operator runs the stop command, **Then** the Function App's state transitions to `Stopped` and its resource and configuration are preserved (FR-005).
2. **Given** the Function App is stopped, **When** a request is made to its old hostname, **Then** the request does not return a successful chat response (FR-005).
3. **Given** the Function App is stopped, **When** the deployed SWA is used end to end, **Then** chat continues to work because it already targets the Container App (FR-001, FR-005).
4. **Given** the Function App is stopped, **When** the operator inspects the resource group, **Then** `Microsoft.Web/sites yh5ax4ws5lr3k-func-movie-tracker` is still present (not deleted). Full rollback of the cutover is a composite action — `az functionapp start` to make the old backend serve again, revert the frontend's `chatBaseUrl` edit, and redeploy the Static Web App so the browser targets the Function App again — not a single-command undo (FR-006).

### Edge Cases

- **Static Web App preview environments** (pull-request-generated hosts like `https://green-mud-037bbdc1e-123.5.azurestaticapps.net`): The tightened CORS policy allows only the production SWA origin. Preview environments calling the Container App chat API from a browser will be blocked by CORS. This slice does not add preview origins to the allowlist; a follow-up slice may introduce a wildcard-per-environment pattern if preview environments need live chat. The preview-vs-prod gap is accepted here as the price of removing `*`.
- **The frontend repository is in a different working directory** (`C:\projects\dev\movie-tracker-app`): The actual code change for User Story 1 happens outside this repository. The URL update, its commit, and its SWA redeploy are owned by that repo's workflow. This spec drives the change and its verification; it does not pretend the file lives in this repo.
- **The frontend has only one environment file** (`src/enviroments/enviroments.ts`, singular, hard-coded): There is no `environment.prod.ts` / `environment.dev.ts` split today. The cutover edits that one file. If the frontend later adopts per-environment builds, that is out of scope.
- **The Container App's ingress CORS policy is the only CORS surface**: `MovieTracker.Api/Program.cs` registers no ASP.NET Core CORS middleware. The entire tightening happens at the Bicep ingress layer. If a future slice adds application-level CORS, this slice does not pre-empt it.
- **The Function App is not reachable from the current CLI auth context**: `az functionapp show` from the available logins (two subscriptions in tenant `cf732866-…`) does not locate `yh5ax4ws5lr3k-func-movie-tracker`. The operator may need to log in to a different subscription or tenant to run the stop in User Story 3. If the Function App has already been stopped or deleted by prior work, User Story 3 is a no-op and the slice MUST record that outcome rather than fabricate a stop action.
- **The Container App URL changes**: The user-supplied Container App FQDN `movie-tracker-api.politeocean-1c0085f8.westus3.azurecontainerapps.io` embeds a per-environment unique suffix. If the Container App Environment is recreated (and the suffix changes), the frontend's hardcoded URL goes stale. This slice does not introduce an output-based or config-driven URL resolution; the operator accepts the hardcoded URL and would re-cut over if the environment is rebuilt.
- **A browser serving mixed content**: The SWA is HTTPS, the Container App is HTTPS. No `http://` origin need be considered.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: The frontend repository's single source of the chat API base URL (`C:\projects\dev\movie-tracker-app\src\enviroments\enviroments.ts`, the `chatBaseUrl` entry) MUST be updated to `https://movie-tracker-api.politeocean-1c0085f8.westus3.azurecontainerapps.io/api/chat`, replacing the current `https://yh5ax4ws5lr3k-func-movie-tracker.azurewebsites.net/api/chat`. The path suffix `/api/chat` MUST be preserved exactly so that `${chatBaseUrl}/start` and `${chatBaseUrl}/${chatId}/ask` continue to compose the same route shape the two chat endpoints expose. No other file in the frontend is edited by this slice.

- **FR-002**: No new chat endpoints, new configuration keys, new environment variables, new CORS middleware, new ASP.NET Core services, new frontend services, or new frontend environment files MUST be introduced. The cutover is a URL swap and a CORS-origin swap only. If a non-trivial change in either repo seems required to make the cutover work, the first assumption is that the Container App already supports the frontend's existing calls (slices 001-005 ported them); the second assumption is that the task is out of scope for this slice.

- **FR-003**: `infrastructure/container-app.bicep`'s ingress `corsPolicy.allowedOrigins` MUST be changed from `['*']` to the Function App's historical origin set, materialized as `['https://green-mud-037bbdc1e.5.azurestaticapps.net', 'http://localhost:4200']`. The first entry is the `defaultHostname` of the `movie-tracker-app` Static Web App, prefixed with `https://`. The second entry is Angular's default `ng serve` port, which is the only localhost dev origin the frontend uses (confirmed from `movie-tracker-app/package.json`'s Playwright scripts, which use `PLAYWRIGHT_BASE_URL=http://localhost:4200`). The other `corsPolicy` fields (`allowedMethods`, `allowedHeaders`, `allowCredentials: false`, `maxAge: 3600`) MUST remain unchanged. The change MUST be deployed through the existing GitHub Actions Bicep workflow; no portal edit of the ingress CORS is permitted (per Constitution principle II).

- **FR-004**: The resulting `allowedOrigins` list MUST contain exactly the two Function-App-parity entries from FR-003, in that order. A `['*']` entry, a `['*', '<swa-url>']` combination, any wildcard subdomain variant (`'https://*.5.azurestaticapps.net'`), or any additional origin not in FR-003's set is rejected. A code reviewer verifying this slice MUST be able to confirm the two-entry rule by reading `container-app.bicep` without opening any other file.

- **FR-005**: The Function App `yh5ax4ws5lr3k-func-movie-tracker` MUST be stopped via `az functionapp stop` using the operator's Azure CLI authenticated to the subscription that hosts it. The operator MUST first resolve the hosting subscription and resource group for the Function App through an explicit authenticated search (not infer it from a prior guess), and MUST then run the stop against the resolved scope. The stop MUST happen only after User Story 1 and User Story 2 have been manually verified against the deployed Static Web App and the deployed Container App policy. If the Function App is already in `Stopped` state at the time this step is reached, the slice records "already stopped" and takes no further action. If the Function App cannot be located in any accessible subscription after resolution, the operator records that outcome and surfaces it to the slice owner; the slice MUST NOT assume absence equals a prior stop.

- **FR-006**: The Function App MUST NOT be deleted. Its resource, App Settings, deployment slots, Key Vault secret references, and role assignments MUST remain intact. No `az functionapp delete`, `az resource delete`, or portal delete is used in this slice. The resource stays in the resource group with `state: Stopped`. Full rollback is a composite three-step action — `az functionapp start`, revert the frontend's `chatBaseUrl` commit, redeploy the Static Web App — not a single-command undo; this slice preserves the resource so step one of that rollback remains available.

- **FR-007**: `.gitignore` MUST NOT be touched by this slice. No new files MUST be added to `.gitignore` under the pretext of "temporary cutover artefact"; any temporary file either stays untracked by local convention (not by repo-wide ignore) or is not created in the first place.

- **FR-008**: No automated tests, Playwright specs, Postman collections, or CI jobs MUST be added for the cutover. Functional verification is manual (DevTools Network tab for US1, `curl -X OPTIONS` for US2, `az functionapp show` for US3), matching slices 001-005's manual-verification stance. The Constitution's existing quality gates (the `Validate Bicep` workflow, the `What-If` workflow, and the per-stage Codex cross-review) MUST still pass; a what-if showing an unexpected delete or replace blocks the merge. "Manual verification" names how the three in-scope behaviours are observed, not a waiver of the gates the Constitution already requires.

- **FR-009**: The tightened ingress CORS policy MUST be deployed and verified on the live Container App before the post-CORS re-run of User Story 1's end-to-end test. Ingress CORS is an application-scope property on `Microsoft.App/containerApps`, so changing `allowedOrigins` does not by itself produce a new template revision; verification is "the deployed policy returns the new value" (for example `az containerapp show --name movie-tracker-api --resource-group RG-MovieTracker-Demo --query 'properties.configuration.ingress.corsPolicy.allowedOrigins'` returns the two-entry Function-App-parity array), not "a new revision exists." The single-active-revision rule from the Constitution's Azure Platform Constraints is unchanged and is unaffected by this slice.

- **FR-010**: The Codex cross-review MUST run after each of the four Spec Kit stages for this slice (`specify`, `plan`, `tasks`, and `implement`), repeating up to six rounds per stage, with each round's remit being to cut inflated or overkill work and keep the cutover focused on the user-specified scope items (frontend `chatBaseUrl` swap, Container App ingress CORS parity set, local-run documentation, Function App `stop`-last). If round 6 is not approved at any stage, work stops and the open findings go to the owner (per Constitution).

- **FR-011**: The frontend's chat API base URL is baked at build time by Angular's `ng build` (consumed from `src/enviroments/enviroments.ts`), so a `chatBaseUrl` edit MUST be followed by a Static Web App redeploy before User Story 1 can be verified. The redeploy is triggered by pushing the URL commit to `main` in `C:\projects\dev\movie-tracker-app`, which fires the existing `.github/workflows/azure-static-web-apps-green-mud-037bbdc1e.yml` workflow — build, deploy to staging slot, run Playwright E2E against staging, promote to production on green. This slice MUST NOT edit that workflow, add new workflow steps, or modify the Playwright tests. The current Playwright suite (`e2e/chatbot-search/chatbot-search.spec.ts` and the five other `*.spec.ts` files, inspected 2026-10-26) only asserts on UI visibility and enabled-state; it does not call the chat API (`sendChatMessage` is declared but never invoked), so the staging-slot host (`green-mud-037bbdc1e-staging.5.azurestaticapps.net`) being absent from FR-003's parity set does not block staging E2E. If a future test adds a real chat-API call, that call will fail CORS on staging and promotion will block; adding a staging origin to the allowlist is explicitly out of scope for this slice. If existing or future E2E fails on staging for any other reason, the operator surfaces that as a separate finding and does not patch the test to force a pass.

- **FR-012**: The slice MUST produce a one-page local-run guide for operators that documents how to run the Angular frontend locally (`npm start` / `ng serve` at `http://localhost:4200`) against the deployed Container App. The guide itself MUST be authored entirely inside `specs/006-cutover/**` (no new files or edits elsewhere in this repository solely to support the guide). The runbook it documents does include the operator's own `enviroments.ts` edit in the frontend repo — that is the same edit FR-001 already specifies, not a new one. The guide MUST state: (a) the single frontend edit required (the same `chatBaseUrl` swap in `enviroments.ts`); (b) the dev server command; (c) that the Container App's tightened CORS (FR-003) already includes `http://localhost:4200`, so no CORS workaround is needed; (d) how to verify the local app is actually hitting the Container App (DevTools Network tab, same evidence as US1). The guide lives in `specs/006-cutover/quickstart.md`.

- **FR-013**: The slice MUST NOT touch any of the five known-untracked local files in `C:\projects\dev\movie-tracker-app`: `.claude/`, `.github/copilot-instructions.md`, `copilot-instructions.md`, `movietracker-demo.mp4`, `test-results/`. These are the operator's local developer artefacts and are out of scope for this cutover. The sole frontend edit the slice makes is to `src/enviroments/enviroments.ts`.

- **FR-014**: User Story 3 (the Function App stop) MUST be the last operational action in this slice. The ordering is: (1) merge the Container App CORS change (US2's Bicep edit) and let the deploy workflow apply it; (2) commit the frontend `chatBaseUrl` change on `main` in the frontend repo and let the SWA workflow build + stage + E2E + promote; (3) verify US1 against the deployed SWA; (4) verify US2 preflights against the deployed Container App; (5) only after steps 3 and 4 pass, stop the Function App. The slice MUST NOT stop the Function App before step 4 completes successfully.

### Out of Scope *(explicitly excluded from this feature)*

- **New frontend environment splits** (`environment.prod.ts`, `environment.dev.ts`, build-time replacements, Angular file-replacements configuration). The current single `enviroments.ts` is edited in place.
- **New frontend configuration mechanism** (reading the API base URL from `staticwebapp.config.json`, from an injected `window.__env`, from a build arg, from an environment variable baked at deploy time). The hardcoded URL is swapped and that is all.
- **ASP.NET Core CORS middleware** (`services.AddCors`, `app.UseCors`, a `Cors` section in `appsettings.json`). The ingress CORS at the Container App layer is the only CORS surface this slice touches.
- **Static Web App preview origin allowlisting**, wildcard subdomain patterns, or a per-environment Container App ingress with per-environment allowlists. Preview environments are documented as out-of-scope in the Edge Cases section and the slice does not attempt to serve them.
- **Deletion** of the Function App, its App Settings, its deployment slots, its linked Key Vault secrets, its role assignments, or the `uniqueString()` prefix pattern the Function App's bicep uses for its names. The Function App is stopped only.
- **Removal of the Function App's bicep** from the backend repository (`C:\projects\dev\movie-tracker-backend`). The backend repo is not touched by this slice; a follow-up slice there may retire the Function App's bicep.
- **Removal of Function App App Settings, Function Keys, Managed Identity role assignments, or any App Settings referencing shared resources** (Cosmos keys the Function App held, Key Vault access policies). These stay as-is so that step one of the three-step rollback (`az functionapp start`, revert the frontend URL commit, redeploy the SWA) remains available.
- **New endpoints, new health probes, new resilience policies, new DI registrations, new telemetry instruments, new logging categories.** Slices 001-005 already brought the Container App to parity; this slice adds nothing on top.
- **Changing the Container App's workload profile, scaling rules, revision mode, probes, env vars, secret names, Key Vault references, or managed identity**. The CORS allowlist is the only container-app property this slice edits.
- **Changing the Static Web App resource**, its `staticwebapp.config.json`, its route rules, its linked backend, its role assignments, or its managed identity. The SWA is a URL input to this slice, nothing more.
- **A diagnostic settings resource, a monitor alert, a dashboard, an action group**, or any new observability surface tied to the cutover. Existing App Insights telemetry (slice 005) is enough to confirm traffic shift.
- **Automated verification** (Playwright e2e against the SWA, Postman monitors, synthetic probes, CI deployment smoke tests). Manual verification per the Independent Tests above is the functional-correctness gate; the Constitution's Validate Bicep, What-If, and per-stage Codex cross-review gates still apply on top (see FR-008).
- **A rollback script**. Rollback is a three-step composite (`az functionapp start`, revert the frontend URL commit, redeploy the SWA); the slice documents those three steps in FR-006 and does not add orchestrating code.
- **Data migration, chat-history transfer, or active-session continuity**. Each backend writes chat sessions to its own store, so sessions created on the Function App are not visible on the Container App and vice versa. Users with an in-flight session on the Function App at cutover time start a new session on the Container App; no code or runbook step attempts to replay, port, or merge sessions across backends. The slice does not touch Cosmos data on either side.
- **Shared-state reconciliation**. If the Function App's Cosmos database and the Container App's Cosmos database contain any overlapping documents (chat history, user profiles, cached lookups), the slice makes no reconciliation guarantee. The port rule ("no new features, config or endpoints") excludes writing any migration or dual-write code.
- **Rotation or deletion of the Function App's secrets** (its hosting storage keys, its App Insights connection string, its Function Keys). Stopped Function App keys are stale but not compromised; this slice does not rotate.
- **Changing the Container App URL** or introducing a custom domain / CNAME for the API. The autogenerated FQDN is used as-is.
- **A `.gitignore` edit**. Explicitly rejected by FR-007 at the user's request.
- **Any change the Codex cross-review flags as overkill or feature-creep**. The review's remit (per the Constitution) is to cut inflated work; its findings tighten this scope rather than expand it.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: After the frontend redeploy, 100% of chat requests observed during one complete manual chat session on the production SWA land on the Container App host; 0% land on the Function App host. Measured in the browser's DevTools Network tab across one `start` + at least two `ask` exchanges.
- **SC-002**: A `curl -i -X OPTIONS` preflight against `/api/chat/start` with `Origin: https://green-mud-037bbdc1e.5.azurestaticapps.net` returns `Access-Control-Allow-Origin: https://green-mud-037bbdc1e.5.azurestaticapps.net` (exact echo, not `*`). The same preflight with `Origin: http://localhost:4200` returns `Access-Control-Allow-Origin: http://localhost:4200`.
