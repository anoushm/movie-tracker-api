## User Scenarios & Testing *(mandatory)*

### User Story 1 - Score the current agent on demand (Priority: P1)

The owner runs the evaluation harness locally to produce a small, easy-to-explain demo score. The harness asks the agent about ten questions — eight per-check templated cases built from three live run titles plus two hand-written plot anchors — grades each answer with the framework's `LocalEvaluator`, and prints a table with one row per case plus a totals line. Each produced case runs once per run, and the grading path is intentionally decentralized — adding a new check kind on the **grading side** is one new `IEvalCheck` file plus one new template entry; the full edit surface (expected record, truth-fetch branch, enum/order updates) is listed in FR-022.

**Why this priority**: Without a repeatable score, there is no cheap way to tell whether a change to prompts, tools, or model configuration helped or hurt. The small-and-explainable run size makes the harness usable in a demo and in a daily inner loop.

**Independent Test**: Run the harness against the current agent state. The run completes without the owner starting the API in another window, prints a results table with roughly ten rows (eight templated cases + two plot anchors, minus any templated case that failed to qualify), and ends with a total score such as `<passed> / <total>`.

**Acceptance Scenarios**:

1. **Given** the API project builds and the owner has the required third-party keys configured where the API normally reads them, **When** the owner runs the harness from the repository, **Then** the harness hosts the API in its own process, asks each case question once in a fresh chat session, and prints a table and total score to the console.
2. **Given** the harness just finished a run, **When** the owner inspects the saved results file, **Then** the file contains the run timestamp, the overall totals, one entry per case with id, check kind, pass/fail, and a short reason, and the per-check pass/total counts the next run needs to print the per-check comparison.
3. **Given** a required third-party key is missing from the configuration source the API uses locally, **When** the owner runs the harness, **Then** the harness stops before asking any question and prints a message that names the missing key.
4. **Given** the harness has graded every case, **When** the owner inspects the output, **Then** every pass/fail decision — except cases pre-marked FAIL with reason `no truth value` under FR-016 (recorded before any evaluator runs) and cases whose chat call failed under FR-015 (recorded with the error message as reason, no evaluator invoked) — was produced by an `IEvalCheck` run through `Microsoft.Agents.AI.LocalEvaluator`, and the harness reads pass/fail and reason directly from the `AgentEvaluationResults` the framework returned — no captured variables, no pipe-delimited expected data, no central if-chain grader.

---

### User Story 2 - See what changed since the last run (Priority: P2)

Before saving a new run, the harness loads the previous run's results (if any) and tells the owner how the score moved for each check kind and overall. This turns a single score into a signal the owner can act on when iterating on the agent.

**Why this priority**: The score on its own does not tell the owner where to look. A per-check comparison — one line per check kind, plus an overall line — points at the specific capability that regressed or improved without forcing the owner to read per-id flip lists that are noisy when generated cases come from live data that shifts between runs.

**Independent Test**: Delete the saved results file, run the harness; confirm no comparison section prints and a results file is written. Run again without changing anything; confirm the harness prints one line per check kind in the form `<check>: <prev passed>/<prev total> -> <cur passed>/<cur total>` plus an overall `total: <prev passed>/<prev total> -> <cur passed>/<cur total>`.

**Acceptance Scenarios**:

1. **Given** no previous results file exists, **When** the owner runs the harness, **Then** the harness prints the current totals with no comparison section and still writes the results file.
2. **Given** a previous results file exists, **When** the owner runs the harness, **Then** the harness prints one comparison line per known check kind plus an overall `total:` line, matched by check kind rather than by case id.
3. **Given** a check kind existed in the stored file but did not produce a case in the current run (or vice versa), **When** the owner runs the harness, **Then** the absent side renders as `-` so the shape change is visible.

---

### User Story 3 - Grade against live third-party truth (Priority: P3)

Every templated case is built from live third-party data at run time, graded against values fetched directly from the same third-party sources for this run. This keeps the evaluation surface fresh without the owner editing a file.

**Why this priority**: The two hand-written plot anchors catch regressions on story-based search for stable titles the owner picked. The templated cases catch regressions the owner did not think to write a case for, and because the run titles come from regional popular lists they also exercise the agent on non-US films.

**Independent Test**: Run the harness and observe one row per templated case whose id identifies the template plus a slot number. The row text reflects titles drawn from the current regional popular lists. Rerunning later, when those lists have shifted, produces rows about different titles while the two hand-written plot-anchor rows stay stable.

**Acceptance Scenarios**:

1. **Given** the third-party movie database is reachable and the required key is configured, **When** the harness builds the generated case set, **Then** it selects **three** titles for this run — one from the third-party popular list in region `US`, one in region `IN`, and one in region `SE` — picking a random page in `1..5` per region. The three titles MUST be unique across regions (by the third-party movie-database id); on a duplicate the harness picks again until three distinct titles are chosen. The harness prints a one-line "Popular titles for this run" summary tagging each title with its region.
2. **Given** a generated case, **When** the harness grades the agent's answer, **Then** it passes when the agent's reply meets that template's specific pass rule (see FR-005).
3. **Given** the owner wants reproducibility of the hand-written results, **When** they inspect the committed cases file, **Then** it holds exactly the two plot-anchor cases verbatim, so the same two plot-anchor questions are asked on every run regardless of what the regional popular lists contain.
4. **Given** a templated check is conditional (`trailer` only when the selected movie has at least one YouTube trailer), **When** the selected title does not qualify, **Then** the harness prints that the check produced zero cases and the run still completes.

---

### Edge Cases

- `asksClarification` was explicitly removed in the rework. No check pins an "expected FAIL" outcome in this slice; every case is graded normally against whatever the agent returns at run time.
- Generated case ids are `<templateId>-<slot>` where slot is `1..3` (the 1-based index of the selected run title). The same id may refer to a different title between runs because the regional popular lists shift; the per-check comparison deliberately does not rely on per-id stability.
- Cases run one at a time. A problem with one case does not reorder or corrupt the rest of the table.
- Each case, except those pre-marked FAIL under FR-016, is asked exactly **once**, in a fresh chat session. There is no two-repetition logic.
- The `followUpDirector` case is multi-turn: the harness opens one chat, sends turn 1 ("Tell me about {title} ({year})"), discards the turn 1 answer, sends turn 2 ("Who directed it?") on the same chat, and grades only the turn 2 answer.
- If the in-process API call for a case fails (non-2xx response, timeout, or response that cannot be parsed into the expected answer plus funny-fact plus movie-list shape), the harness records that case as FAIL with the error message as its reason and continues to the next case.
- If a third-party truth value is missing for a produced case (no crew member with job `Director`, no cast member with `order` 0, no release date, no IMDb id, open-movie-database `imdbRating == "N/A"`, no overview text, no genre on the selected movie, no acting credits for the resolved actor), the harness records the owning case as FAIL with reason `no truth value` and makes no chat call. The `trailer` check is instead gated by the qualification rule in FR-007: when the selected movie has no YouTube trailer, the `trailer` template produces **no case at all** rather than a `no truth value` FAIL.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: The harness MUST run as a standalone console program the owner invokes on demand from the repository, with no separately started API process required.
- **FR-002**: The harness MUST host the API in the same process it runs in and communicate with it only through the API's HTTP contract (start a new chat session, then submit a chat turn for the case's question), so the harness exercises the same request path that a real client would.
- **FR-003**: For each case that produced a chat response (i.e. not a case pre-marked FAIL under FR-016, and not a case whose chat call failed under FR-015), the harness MUST build an `EvalItem` with: `Response` set to the agent's answer text (the chat response's `turn.text`), `Context` set to the UTF-8 JSON serialization of an **actual-response payload** that bundles both the chat response's `funnyFact` field and the chat response's `turn.movieList` projected to the fields any check kind needs (per-entry: TMDb id, title, release date, genre names, genre ids), and `ExpectedOutput` set to the UTF-8 JSON serialization of the case's typed **expected-data** payload (shape per check kind — see data-model.md). The harness MUST then group all such items by check kind and, for each group, construct one `Microsoft.Agents.AI.LocalEvaluator` holding that check's single `FunctionEvaluator` (wrapping the check's `IEvalCheck`) and call `EvaluateAsync` once per group. The harness MUST read pass/fail and reason directly from the `AgentEvaluationResults.Items[i].Metrics[checkName]` `BooleanMetric` the framework returns — no captured variables, no pipe-delimited `ExpectedOutput`, and no central if-chain over check kinds in the **grading path** (see FR-022 for the explicit scope of this ban).
- **FR-004**: The hand-written case file `MovieTracker.Evals/eval-movie-cases.json` MUST contain exactly two plot-anchor cases and nothing else: `plot-ship-sinks` (expected `["Titanic"]`) and `plot-mob-family` (expected `["The Godfather"]`), each with check `listIncludes` and an `expected` array of titles. The `listIncludes` check passes when **every** entry in `expected` is in the answer per the movie-in-answer rule (FR-023); the answer may list other movies in addition.
- **FR-004a**: The case loader MUST only enforce that `id` values are unique across the file. It MUST NOT enforce a fixed entry count, a fixed set of ids, or any per-check-kind distribution.
- **FR-005**: The template file `MovieTracker.Evals/eval-movie-templates.json` MUST contain exactly eight template entries covering these check kinds, in each case using the shown question shape. Templates that use more than one chat turn carry a `turns` array holding the turn texts in order; single-turn templates use a `template` string field.
  - `director` — single-turn `"Who directed {title}?"`; truth = the TMDb crew member whose `job` is `Director`; passes when the answer text contains that name (case-insensitive).
  - `actorFilmography` — single-turn `"Show me movies starring {actor}"` where `{actor}` is the cast member whose `order` is `0` on the selected movie; truth = that actor's name plus the set of TMDb movie ids and the set of movie titles (case-insensitive) in that actor's TMDb acting credits; passes when the chat response's `turn.movieList` is non-empty AND every entry in it matches a movie in the actor's acting-credits set by the item-in-filmography rule (FR-023 point 2): first by TMDb id match against the id set, then by case-insensitive title match against the title set.
  - `identifyByPlot` — single-turn `"Which {year} movie is this: {overview}"` where `{year}` is the four-digit year from the selected movie's TMDb `release_date` and `{overview}` is the TMDb `overview` for the selected movie with the movie's title words removed (case-insensitive word-level strip); truth = the source movie (TMDb id and title); passes when the source movie is in the answer per FR-023 (id-first in `turn.movieList`, title fallback in the answer text).
  - `genreDecade` — single-turn `"Show me {genre} movies from the {decade}s"` where `{genre}` is one of the selected movie's TMDb genre names and `{decade}` is the four-digit decade start taken from its `release_date` (e.g. `release_date` starting `1997` → `1990`); truth = that genre's TMDb id, that genre's TMDb name, and that decade start; passes when `turn.movieList` is non-empty AND, for every entry, (the truth genre id is in that entry's `genreIds` OR, as fallback, the truth genre name is in that entry's `genreNames`) AND that entry's `releaseDate` has a year inside that decade.
  - `rating` — single-turn `"What is the IMDb rating of {title} ({year})?"` where `{year}` is the four-digit year from the selected movie's TMDb `release_date`; truth = the OMDb `imdbRating` for the IMDb id TMDb reports for the selected movie; passes when the answer text contains that rating (case-insensitive).
  - `trailer` — single-turn `"Show me the trailer for {title} ({year})."` where `{year}` is the four-digit year from the selected movie's TMDb `release_date`; truth = the set of YouTube video keys the TMDb `/movie/{id}/videos` endpoint returns for the selected movie filtered to `site == "YouTube"` **and** `type == "Trailer"` (teasers, clips, featurettes, etc. are excluded). The template produces a case only when that set is non-empty. Passes when **any** `[TRAILER]<url>[/TRAILER]` substring in the answer carries a YouTube video key (the value after `v=`) that is in the truth set — the answer may contain multiple tagged URLs, and finding one qualifying key is enough.
  - `followUpDirector` — multi-turn with `turns` = `["Tell me about {title} ({year})", "Who directed it?"]` in the same chat session, where `{year}` is the four-digit year from the selected movie's TMDb `release_date`; truth = the TMDb crew member whose `job` is `Director` for the selected movie; passes when the **turn 2** answer text contains that name (case-insensitive). The turn 1 answer is not graded.
  - `funnyFactNotEmpty` — single-turn `"Tell me a fun fact about {title} ({year})."` where `{year}` is the four-digit year from the selected movie's TMDb `release_date`; truth = (no pre-resolved truth value needed beyond the year); passes when the `funnyFact` field on the chat response is not null and not empty.
- **FR-006**: The run's three titles MUST be selected at run time from the third-party movie database's `movie/popular` endpoint in three regions — `US`, `IN`, `SE` — taking one title per region. For each region, the harness MUST pick a random page number in `1..5` and one random title from that page's results. Titles MUST be unique across regions (by the third-party movie-database id); on a collision the harness MUST pick again within the chosen page for the affected region until three distinct titles are chosen. The harness MUST print a "Popular titles for this run" line that tags each title with its region.
- **FR-007**: Each template produces **zero or one** case per run. A title-based template picks one of the three run titles (slot `1..3`) at random using `System.Random.Shared` and runs that single case for that selection. The `trailer` template qualifies only when the selected movie has at least one YouTube trailer; non-qualifying runs produce no case for `trailer`. All eight templates are expected to produce a case on a typical run, so the total case count is typically 8 template + 2 anchor = 10. The harness MUST print a one-line produced-count summary for every template whose produced-case count can be zero (`trailer`).
- **FR-008**: Generated cases MUST exist only in memory for the duration of the run. The harness MUST NOT write generated cases to any file, committed or otherwise. Generated case ids MUST take the form `<templateId>-<slot 1..3>` where `slot` is the 1-based index of the selected run title.
- **FR-009**: Each case, except those pre-marked FAIL under FR-016, MUST be asked **exactly once**. Single-turn cases use one `GET /api/chat/start` to open a fresh chat session plus one `POST /api/chat/{chatId}/ask/v2` to submit the question. Multi-turn cases use one `GET /api/chat/start` plus one `POST /api/chat/{chatId}/ask/v2` per turn, all on the same `chatId`. There is no two-repetition logic and no retry.
- **FR-010**: Every case row MUST be recorded with id, check kind, pass/fail, and a short human-readable reason. After all cases complete, the harness MUST print one console table with one row per case, followed by a totals line of the form `<passed> / <total>`.
- **FR-011**: Before overwriting the stored results file, the harness MUST load the previous run's stored results from `MovieTracker.Evals/results/last-run.json` if the file exists. When a previous file exists, the harness MUST print one comparison line per known check kind in the form `<check>: <prev passed>/<prev total> -> <cur passed>/<cur total>` plus an overall `total: <prev passed>/<prev total> -> <cur passed>/<cur total>` line, where each side's `passed/total` is `-` when that check kind produced no cases in that run. When no previous file exists, the harness MUST skip the comparison section gracefully and still proceed to write the current results.
- **FR-012**: The harness MUST write every run's results to the single file at `MovieTracker.Evals/results/last-run.json`, containing the run timestamp, the overall totals, one entry per case (id, check kind, pass/fail, reason), and the per-check pass/total counts the next run needs to print the per-check comparison.
- **FR-013**: The harness MUST obtain the third-party movie-database key and the open-movie-database key from the same configuration source the API already uses when running locally. It MUST NOT hard-code a key, prompt the owner at run time, or fall back to a default.
- **FR-014**: If either of those two keys is missing from the configuration source at startup, the harness MUST stop before asking any case question and print a message that names the missing key.
- **FR-015**: If the in-process API call for a case fails (non-2xx response, request timeout, or a response that cannot be parsed into the expected answer plus funny-fact plus movie-list shape), the harness MUST record that case as FAIL with the error message as its reason and MUST continue running the remaining cases. The run MUST still produce the full table and write the results file.
- **FR-016**: If a third-party truth value is missing for a case that was produced (no crew member whose job is `Director`, no cast member whose `order` is `0`, no release date, no IMDb id, open-movie-database `imdbRating == "N/A"`, no overview text, no genre name, no acting credits for the resolved actor), the harness MUST record that case as FAIL with reason `no truth value` and MUST NOT make any chat call for that case. This rule does not apply to the `trailer` template, which is instead gated by the qualification rule in FR-007 and produces no case at all for a selected movie with no YouTube trailers.
- **FR-017**: The slice MUST NOT change any file outside `MovieTracker.Evals/` and `specs/008-eval-harness/`. The one-line `MovieTracker.Evals` project registration in `movie-tracker-api.slnx` is a historical carry-over from the original slice (it was added when the project first appeared and stays in place across every rework); this rich-eval rework does not re-touch it. In particular the slice MUST NOT change any file under `MovieTracker.Api/`, `infrastructure/`, `.github/`, `CLAUDE.md`, or any prior spec folder (001 through 007), and MUST NOT modify `movie-tracker-api.slnx` further.
- **FR-018**: The harness MUST host the API via `WebApplicationFactory<global::Program>` where `global::Program` is the `public partial class Program` the .NET SDK auto-generates for the API project. If this entry-point binding does not compile without a change to `MovieTracker.Api/`, work MUST stop at that point and the owner decides what to change.
- **FR-019**: The harness MUST remain usable without changes when the underlying agent evolves from a single-agent to a multi-agent arrangement, because it only interacts through the API's chat-turn contract.
- **FR-020**: `MovieTracker.Evals/MovieTracker.Evals.csproj` MUST reference `Microsoft.Agents.AI` version `1.17.0`. The implementer MUST verify against the installed 1.17.0 assembly, before writing the grading path, that every item below exists and is usable as FR-003 describes:
  1. Type `Microsoft.Agents.AI.LocalEvaluator` with constructor `LocalEvaluator(params Microsoft.Agents.AI.EvalCheck[] checks)` and instance method `Task<Microsoft.Agents.AI.AgentEvaluationResults> EvaluateAsync(IReadOnlyList<Microsoft.Agents.AI.EvalItem> items, string evalName = "Local Eval", CancellationToken ct = default)`.
  2. Static method `Microsoft.Agents.AI.FunctionEvaluator.Create(string name, Func<Microsoft.Agents.AI.EvalItem, Microsoft.Agents.AI.EvalCheckResult> check)` returning `Microsoft.Agents.AI.EvalCheck`.
  3. Type `Microsoft.Agents.AI.EvalItem` with constructor `EvalItem(string query, string response)` and settable properties `Response` (string), `Context` (string?), `ExpectedOutput` (string?).
  4. Type `Microsoft.Agents.AI.EvalCheckResult` with constructor `EvalCheckResult(bool Passed, string Reason, string CheckName)`.
  5. Type `Microsoft.Agents.AI.AgentEvaluationResults` with a public collection `Items` whose element type exposes a `Metrics` dictionary keyed by check name, whose value for a `FunctionEvaluator`-produced result is a `Microsoft.Extensions.AI.Evaluation.BooleanMetric`.
  6. Type `Microsoft.Extensions.AI.Evaluation.BooleanMetric` with a readable boolean-pass member and a readable reason-string member (the exact property names the harness reads for `boolean.Value` and `boolean.Reason`-equivalent — if the installed shape differs, the harness MUST stop with a named message and let the owner decide).

  If any of these are not available in 1.17.0 as described, work MUST stop at that point and the owner decides what to change.
- **FR-021**: The slice MUST keep the feature-folder documents consistent with this rich-eval rework: `rich-eval-prompt.md` is authoritative; `rework-prompt.md` and `prompt.md` MUST be updated so no earlier document still describes six run titles, two repetitions per case, the removed check kinds (`leadActor`, `releaseYear`, `trailerFormat`, `asksClarification`, `plotSearch`), the captured-variable `CheckEvaluator`, the pipe-separated `ExpectedOutput` encoding, or any other element superseded by this spec. `spec.md`, `plan.md`, `research.md`, `data-model.md`, every file under `contracts/`, `quickstart.md`, and `tasks.md` MUST be updated to match.
- **FR-022**: Every per-check grading function MUST live in its own file as a `public sealed class <CheckName>Check : IEvalCheck`. `IEvalCheck` is a harness-defined interface with `string Name { get; }` and `EvalCheckResult Evaluate(EvalItem item)`. On the **grading side** no central registry, dispatcher, or if-chain over check kinds MUST exist — the harness obtains its `IEvalCheck` instances via reflection over the executing assembly, and the per-check `IEvalCheck.Evaluate` bodies are the sole grading logic. This central-grader ban deliberately does **not** reach non-grading concerns: the `TemplateCheck` data-shape enum, the fixed presentation order used by the per-check comparison printer, and the per-check truth-fetch branches inside `GeneratedCaseBuilder` are allowed (each check kind inherently needs its own TMDb/OMDb lookup logic). Adding a new check kind therefore means: one new `IEvalCheck` file (grading), one new `*Expected.cs` typed record, one new template entry, one new truth-fetch branch in `GeneratedCaseBuilder`, and — only if the new check reports via a new name — one new entry in the `TemplateCheck` enum and the presentation-order list.
- **FR-023**: Two movie-matching rules apply, depending on the direction of the question:
  1. **Movie-in-answer** (used by `listIncludes`, `identifyByPlot`): the harness asks "does the agent's answer reference this expected movie?" and, when the expected movie carries a known TMDb id (e.g. `identifyByPlot`, where the id came from TMDb), MUST first match that id against the ids in `turn.movieList`. If no id is known (e.g. the hand-written `listIncludes` plot anchors, which carry titles only) or no id match is found, the harness MUST fall back to case-insensitive matching of the expected title against (a) each `turn.movieList` entry's `title` AND (b) `turn.text`; a match in either place counts.
  2. **Item-in-filmography** (used by `actorFilmography`): the harness asks "is each entry in `turn.movieList` a movie from the resolved actor's acting credits?" and MUST, for each `turn.movieList` entry, first match that entry's TMDb id against the actor's filmography-id set, and if no id matches, fall back to case-insensitive title match against the actor's filmography-title set.

  Names and ratings (not movie identifiers) are always checked against `turn.text` directly, case-insensitive.
- **FR-024**: Any C# examples that appear anywhere in this slice's documents (spec, plan, research, data-model, quickstart, tasks, contracts/README) MUST follow the project code style: explicit types (never `var`), braces on every `if`, no inline comments, private fields plain camelCase (no `_`), `I` prefix on interfaces, `Async` suffix on async methods.

### Out of Scope *(per Constitution III)*

- Any model-based or LLM grader; grading is routed through `LocalEvaluator` + per-check `IEvalCheck` only.
- Any dashboard, visualization, scheduled run, hosted monitor, or continuous-integration integration.
- Any new Azure resource, Bicep change, or deployment pipeline change.
- Any change to the API project, infrastructure directory, continuous-integration workflow files, top-level agent-guidance file, or prior spec folders (001 through 007).
- Calling the agent directly in-process (bypassing the API) or calling a separately running API over the network.
- Command-line options, retries, parallel runs, configurable repetitions, random seed, or a per-id flip report.
- Fixing any failing check (every case is graded against the live agent; no outcome is pinned by this spec).

### Key Entities *(include if feature involves data)*

- **Plot-anchor case**: One hand-written case with its `listIncludes` check and the expected titles that check needs. Both entries are stored verbatim in `MovieTracker.Evals/eval-movie-cases.json`.
- **Case template**: A question pattern that uses the applicable placeholders from `{title}`, `{year}`, `{actor}`, `{overview}`, `{genre}`, and `{decade}` (different templates use different subsets — e.g. `actorFilmography` uses `{actor}` and no `{title}`; `identifyByPlot` uses `{year}` and `{overview}`; `genreDecade` uses `{genre}` and `{decade}`; `rating`, `trailer`, `followUpDirector`, and `funnyFactNotEmpty` use `{title}` and `{year}`). `{year}` is the four-digit year from the selected movie's TMDb `release_date`; a template that needs `{year}` and the selected movie lacks a release date records the case as FAIL with reason `no truth value` under FR-016. A named check identifies which truth field to resolve. Eight templates live in `MovieTracker.Evals/eval-movie-templates.json`: `director`, `actorFilmography`, `identifyByPlot`, `genreDecade`, `rating`, `trailer`, `followUpDirector`, `funnyFactNotEmpty`. Multi-turn templates (`followUpDirector`) carry a `turns` array; single-turn templates carry a `template` string.
- **Run title**: One of the three titles the harness selects for this run — one from the third-party popular list in region `US`, one in region `IN`, and one in region `SE`. Each carries the TMDb id (for follow-up lookups), the title text (for placeholder substitution), the region tag (for the "Popular titles" line), and the 1-based slot index (`1..3`, for the generated case id).
- **Generated case**: A case built in memory at run time by picking one of the three run titles and filling the template with data derived from that title. Its id is `<templateId>-<slot 1..3>`.
- **Evaluation item**: `Microsoft.Agents.AI.EvalItem` — the framework-provided per-case input the harness builds for grading. `Response` holds the agent's answer text (`turn.text`); `Context` holds the UTF-8 JSON serialization of the actual-response payload `{ funnyFact, movieList[] }` so `IEvalCheck.Evaluate` can access the funny-fact string AND the structured movie-list the agent returned without captured variables; `ExpectedOutput` holds the UTF-8 JSON serialization of the case's typed expected-data payload (shape per check kind — see data-model.md). "`funnyFact` stays in Context" from the authoritative `rich-eval-prompt.md` is preserved — `funnyFact` is still carried there — alongside the movie-list the movie-list-reading checks need.
- **Per-check evaluator**: One `IEvalCheck` implementation per check kind, wrapped once with `FunctionEvaluator.Create(name, item => check.Evaluate(item))` and attached to a `LocalEvaluator` holding only that one evaluator. The harness constructs nine `IEvalCheck` instances in total (one per check kind).
- **Run result**: A record of one full harness execution: run timestamp, overall totals, the per-case list, and the per-check pass/total counts the next run needs to print the per-check comparison.
- **Results file**: The single JSON document at `MovieTracker.Evals/results/last-run.json` that stores the most recent run result and feeds the comparison on the next run.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: Given the API project builds and the required third-party keys are present in the configuration source, a run produces a scored table and a totals line without the owner starting any other process first.
- **SC-002**: Every grading decision in the table is read from `AgentEvaluationResults.Items[*].Metrics[checkName]` (as `BooleanMetric`) — cases pre-marked FAIL with reason `no truth value` under FR-016 and cases whose chat call failed under FR-015 are recorded before any evaluator runs. No captured variables exist in the grading path, and no central if-chain over check kinds exists in the **grading path** (per FR-022's grading-side scope; truth-fetch branches in `GeneratedCaseBuilder` are allowed because they are not a grader). Every pass/fail decision that goes through MAF comes from one `IEvalCheck` implementation.
- **SC-003**: Each produced case, except those pre-marked FAIL under FR-016, is asked exactly once in a fresh chat session.
- **SC-004**: The run selects three titles — one each from the third-party popular list in regions `US`, `IN`, `SE` — on randomly chosen pages in `1..5`, no title repeated across regions.
- **SC-005**: Given a stored results file, the harness prints one `<prev passed>/<prev total> -> <cur passed>/<cur total>` line per known check kind plus an overall total line in the same form, matched by check kind, not by case id.
- **SC-006**: Removing either required third-party key from the configuration source causes the run to stop before any question is asked, with a message that names the missing key.
- **SC-007**: The only files changed by this rich-eval rework sit under `MovieTracker.Evals/` and `specs/008-eval-harness/`. `movie-tracker-api.slnx` is not re-touched by this rework (the `MovieTracker.Evals` project-registration line is a carry-over from the original slice).

## Assumptions

- The owner runs the harness from Windows with the local configuration they already use to run the API; the harness reads the two third-party keys from the same configuration source the API's local run already reads them from.
- The third-party movie database's regional popular lists are reachable and return at least one title per region on pages in `1..5` when the harness runs. Transient outages are the owner's cue to rerun.
- Each run costs third-party money (model tokens on the API side, third-party database quota on the harness side); the harness is run on demand.
- Each run creates one chat session per executed case in whatever Cosmos DB instance the locally hosted API is configured to use — cases pre-marked FAIL under FR-016 do not create a chat session; the multi-turn `followUpDirector` case uses one chat session for both turns. This is expected and not something the harness tries to clean up.
- The owner commits the single stored results file after each run they want on record; version control is the only historical record of past runs this slice produces.
- The harness can host the API in-process without any change to the API project, binding against the `public partial class Program` the .NET SDK auto-generates for the API (FR-018).
- `Microsoft.Agents.AI` 1.17.0 exposes the members FR-020 requires, and `AgentEvaluationResults.Items` returns a per-item collection whose per-item `Metrics[checkName]` is a `Microsoft.Extensions.AI.Evaluation.BooleanMetric` carrying both pass/fail and reason. If the installed assembly differs, work stops at that point.
